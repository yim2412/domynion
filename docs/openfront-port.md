# openfront 전체 이식 계획

**결정 (2026-08-21):** openfront.io 를 **완전 복제**한 뒤, 그 위에 **증강형 테크트리**를
얹는다. 사용자가 실물 URL 을 주고 "이 게임과 동일하게 만든 뒤 증강같은 테크트리를 추가"
로 확정했다.

같은 날 사용자 요청으로 **이전 설계 결정 기록을 전부 폐기했다.** 그중 두 가지가 지금
작업에 직접 걸리므로 명시해 둔다 — **더 이상 유효하지 않다**:
- "간단 명료 우선 — 복잡도를 늘리는 해법보다 규칙 통합을 먼저" → 전체 복제가 우선한다
- "고정 루트 테크트리는 기각, 드래프트로 확정" → **형태는 다시 열려 있다.**
  P7 에서 처음부터 다시 정한다

출처: `github.com/openfrontio/OpenFrontIO` (main, 2026-08-21 clone).
아래 수치는 전부 **소스에서 직접 읽은 것**이며, 추정하거나 기억으로 적은 것은 없다.
값을 옮길 때는 반드시 이 문서가 아니라 **소스를 다시 확인**할 것 — 이 문서도 사본이다.

## 0. 지금 우리 것과 무엇이 다른가

v0.1 은 openfront 를 **글로 요약한 설명**을 보고 만들었다. 개념은 맞지만 공식이 거의
전부 다르다. 아래가 실측 대조표다.

| | openfront | Domynion v0.1 |
|---|---|---|
| 병력 상한 | `2 × (타일^0.6 × 1000 + 50000)` + 도시레벨합 × 250000 | `250 + 타일 × 22` |
| 병력 성장 | `(10 + 병력^0.73 / 4) × (1 − 병력/상한)` | `상한 × 0.085 × 여유` |
| 지형 | Plains / Highland / Mountain / Ocean / Impassable | 평야 / **숲** / 구릉 / 산악 / 바다 |
| 지형 수치 | `mag` 80/100/120 **와** `speed` 16.5/20/25 — 두 축 | 방어 계수 하나 |
| 칸당 공격측 손실 | `0.6 × A + 0.4 × B` 가중합 (아래 1.2절) | `2.6 × 지형 × (1+충전율×2.2)` |
| 칸당 수비측 손실 | `수비병력 / 수비타일수` (절대값) | 공격 소모 × 0.42 |
| tick 예산 | `within(5×공격/수비 × 2, 0.01, 0.5) × 국경길이 × 3` | `min(90, 6 + 병력×0.055)` |
| 프론티어 | **우선순위 힙** — 싼 지형·내 이웃 많은 칸 먼저 | FIFO 큐, 막히면 앞으로 되돌림 |
| 중립 공격 | **별도 분기** (손실 `mag/5`, 예산 `within(2000×speed/병력, 5, 100)`) | 사람 공격과 같은 공식 |
| 공격 투입 | 사람 `병력/5`, 봇 `병력/20` | 슬라이더 25% |
| tick | 100ms (10Hz) | 50ms (20Hz) |

**우리가 정반대로 만든 것 두 가지** — 되돌려야 한다:
1. 프론티어를 FIFO 로 두고 "막힌 칸은 큐 앞에 되돌린다" 를 테스트로 못 박았다.
   원본은 **싼 칸부터** 먹는 우선순위 힙이다. 그 테스트는 폐기 대상이다.
2. 수비측 손실에 "타일당 병력(절대값)" 을 쓰는 것을 설계 5절이 교착 원인으로 지목해
   폐기했는데, **원본은 그것을 쓴다.** 단, 원본은 그 값을 *비용*이 아니라 *수비측
   병력 손실*에만 쓴다 — 우리가 폐기한 것은 *비용*에 쓴 쪽이다. 둘은 다른 자리다.

## 1. 전투 — 원본 공식 그대로

`src/core/configuration/Config.ts :: attackLogic()`

### 1.1 지형

| TerrainType | mag | speed |
|---|---|---|
| Plains | 80 | 16.5 |
| Highland | 100 | 20 |
| Mountain | 120 | 25 |
| Ocean / Impassable | 공격 불가 | — |

수정자(곱셈, 순서대로):
- 방어초소(DefensePost)가 사거리 30 안에 있으면 `mag × 5`, `speed × 3`
- 낙진(fallout) 타일이면 `mag`·`speed` 에 `falloutDefenseModifier(낙진비율)`
- 공격자가 Human/Nation 이고 수비자가 Bot 이면 `mag × 0.7`
- 같은 팀의 연결 끊긴 수비자면 `mag = 0`

### 1.2 수비자가 플레이어일 때

```
defenseSig = 1 − sigmoid(수비타일수, DEFENSE_DEBUFF_DECAY_RATE, DEFENSE_DEBUFF_MIDPOINT)
largeDefenderAttackDebuff = 0.7 + 0.3 × defenseSig
largeDefenderSpeedDebuff  = 0.7 + 0.3 × defenseSig

largeAttackBonus       = 공격타일 > 100000 ? sqrt(100000/공격타일)^0.7 : 1
largeAttackerSpeedBonus= 공격타일 > 100000 ? (100000/공격타일)^0.6   : 1

defenderTroopLoss = 수비병력 / 수비타일수
traitorMod        = 수비자가 배신자면 0.5 아니면 1

A = within(수비병력/공격병력, 0.6, 2) × mag × 0.8 × largeDefenderAttackDebuff
    × largeAttackBonus × traitorMod
B = 1.3 × defenderTroopLoss × (mag/100) × traitorMod

attackerTroopLoss = 0.6 × A + 0.4 × B
tilesPerTickUsed  = within(수비병력/(5×공격병력), 0.2, 1.5) × speed
                    × largeDefenderSpeedDebuff × largeAttackerSpeedBonus
                    × (배신자면 traitorSpeedDebuff)
```

### 1.3 수비자가 중립(TerraNullius)일 때

```
attackerTroopLoss = 공격자가 봇이면 mag/10, 아니면 mag/5
defenderTroopLoss = 0
tilesPerTickUsed  = within(2000 × max(10, speed) / 공격병력, 5, 100)
```

**공격병력이 많을수록 `tilesPerTickUsed` 가 작아진다** = 한 칸이 예산을 덜 먹는다
= 더 많이 번진다. 우리 v0.1 의 "속도 = f(병력)" 과 방향은 같고 형태가 다르다.

### 1.4 tick 예산과 루프

`attackTilesPerTick(공격병력, 공격자, 수비자, 인접적타일수)`:
```
수비자가 플레이어: within((5×공격병력/수비병력) × 2, 0.01, 0.5) × 인접적타일수 × 3
중립            : 인접적타일수 × 2
```
`인접적타일수` 는 `attack.borderSize() + rand(0,5)` 로 넘어온다 — **국경이 넓을수록
한 tick 에 더 많이 번진다.** 우리에게 없던 축이다.

`AttackExecution.tick()`:
```
예산 = attackTilesPerTick(...)
while 예산 > 0:
    if 병력 < 1: 공격 소멸(퇴각 없음)
    if 큐 비었음: 퇴각 (남은 병력 본국 환원)
    타일 = 큐.dequeue()            # 최소 우선순위
    소유자가 대상이 아니거나 내 영토에 안 접하면 skip (재큐 안 함)
    바다·통행불가면 skip
    이웃을 큐에 넣는다
    (공격손실, 수비손실, 예산소모) = attackLogic(...)
    예산 -= 예산소모;  병력 -= 공격손실;  수비자.병력 -= 수비손실
    정복
    수비자 타일 < 100 이면 통째로 흡수(conquerPlayer)
```

### 1.5 우선순위 힙

`AttackExecution.addNeighbors()`:
```
mag = Plains 1 / Highland 1.5 / Mountain 2 / 그 외 0
priority = (rand(0,7) + 10) × (1 − 내이웃수 × 0.5 + mag/2) + 현재tick
```
**낮은 priority 를 먼저** 꺼낸다. 내 영토에 많이 접한 칸과 싼 지형이 먼저 먹힌다.
`+ 현재tick` 이 있어서 나중에 들어온 칸은 뒤로 밀린다(FIFO 성질을 일부 유지).

## 2. 병력·골드

```
maxTroops = 2 × (타일수^0.6 × 1000 + 50000)
            + Σ(도시 레벨) × 250000
  봇       : /3
  Nation   : 난이도별 ×0.5 / ×0.75 / ×1 / ×1.25

troopIncrease = (10 + 병력^0.73 / 4) × (1 − 병력/상한)
  봇       : ×0.5
  Nation   : 난이도별 ×0.9 / ×0.95 / ×1 / ×1.05
  결과는 상한으로 clamp

시작 병력 = 사람 25000 / 봇 10000 / Nation 난이도별 12500~
공격 투입 = 사람 병력/5 · 봇 병력/20   (사람은 UI 슬라이더로 조절)
보트 투입 = 병력/5

골드 수입 = 사람 100/tick · 봇 50/tick  (× goldMultiplier)
무역선 골드 = 75000/(1+e^(−0.03×(거리−300))) + 50×거리
```

## 4. 동맹·외교

- 동맹 지속 `5분` (호스트가 1~15분 지정 가능, 0 이면 동맹 비활성)
- 동맹 파기 시 **배신자(traitor)** 30초: 방어 ×0.5, 속도 페널티
- 동맹 중 상대를 공격하면 즉시 동맹 파기 + 배신자
- 공격 시작 후 동맹이 맺어지면 그 공격은 자동 퇴각
- 그 외: 금수조치(Embargo), 골드/병력 기부, 이모지, 퀵챗, 팀전

## 4.5 ⚠ 지도 크기 — 이게 P1 의 진짜 난관이다

원본 지도는 우리 것보다 **수백 배 크다.** `resources/maps/*/manifest.json` 실측:

| 지도 | 육지 타일 (원본) | map4x | map16x |
|---|---|---|---|
| Europe | 2,345,907 | 568,335 | 134,751 |
| Africa | 2,183,279 | 537,561 | 130,741 |
| Asia | 1,079,587 | 265,522 | 64,809 |
| World | 651,569 | 158,068 | 37,575 |

**Domynion v0.1 은 4인전에서 1,600칸이다.** 400~1400배 차이다.

공식이 그 규모에 맞춰져 있어서, 작은 지도에 그대로 넣으면 **다른 게임이 된다**:

```
maxTroops = 2 × (타일^0.6 × 1000 + 50000)

  타일      1 →   102,000     (상수 50000 이 지배)
  타일   1600 →   267,400
  타일 100000 → 2,100,000
```

1,600칸 지도에서는 1타일 플레이어와 1,600타일 플레이어의 병력 상한이 **2.6배밖에**
차이 나지 않는다. 영토를 넓히는 의미가 거의 사라진다. `DEFENSE_DEBUFF_MIDPOINT`
(150,000 타일)와 `largeAttackBonus` 문턱(100,000 타일)도 우리 규모에서는 **영원히
발동하지 않는 죽은 가지**가 된다.

따라서 전체 복제는 **지도를 최소 map16x 급(3만~13만 타일)으로 키우는 것을 포함한다.**
그러면 지금 자료 구조가 못 버틴다:

| 지금 | 바꿔야 할 것 |
|---|---|
| `dict[Coord, Tile]` — 타일마다 파이썬 객체 | numpy 배열 3장 (terrain / owner / border) |
| `owned_by()` 가 전수 순회 | 소유 타일 집합을 증분 유지 |
| `frontier()` 가 매번 재계산 | 공격이 들고 다니는 경계 집합 |
| PIL 렌더러 타일당 루프 | 이미 numpy 기반 — 경계선 그리기만 벡터화 필요 |

**P1 은 공식 이식과 자료 구조 교체를 같이 해야 한다.** 둘을 나누면 작은 지도에서
공식을 재게 되는데, 그 측정값은 전부 버려야 한다.

## 5. 이식 순서

각 단계마다 **240판 헤드리스로 재고** 다음으로 넘어간다. 원본과 같은 공식을 넣었는데
결과가 이상하면 옮기다 틀린 것이지 밸런스 문제가 아니다 — 그때는 소스를 다시 본다.

| 단계 | 내용 | 상태 |
|---|---|---|
| **P1a** | 지도를 numpy 배열로 · 원본 `.bin` 118장 로더 (4.5절) | ✅ |
| **P1b** | 지형 3종 · 병력 상한/성장 · attackLogic · 우선순위 힙 · tick 10Hz | ✅ |
| **P2** | 골드 · City/Port/Factory/DefensePost + 건설·업그레이드 | ✅ |
| **P3** | 동맹 · 배신자 · 팀 · 금수 (기부는 P4 의 무역선과 함께) | ✅ |
| **P4** | 수송선 · 무역선 · 기부 · 전함/포탄 · **철도/기차** | ✅ |
| **P5** | 핵(원폭/수폭/MIRV) · SAM 요격 · 낙진 · 지형 파괴 | ✅ |
| **P6** | 둠스데이 클락 · 플레이어 3종·난이도 · **원본 스폰 규칙** · **원본 봇** | ✅ |
| **P7** | **증강형 테크트리를 얹는다.** 형태(드래프트/고정루트/혼합)는 이 시점에 **처음부터** 정한다 — 옛 결정은 폐기됐다 | ⬜ |

P1 을 끝내기 전에는 증강 밸런스를 재지 않는다. 코어가 바뀌면 그 위 수치는 전부 무효다.

### P1 에서 손댈 파일

| 파일 | 무엇을 |
|---|---|
| `core/constants.py` | 숫자 전면 교체. 각 값 옆에 **원본 파일:함수** 를 주석으로 |
| `core/gamemap.py` | **numpy 배열로 재작성** + 숲 제거 → 3종, Ocean/Impassable 구분 |
| `core/state.py` | `max_troops` · `growth_per_sec` 를 원본 공식으로. 충전율 개념 폐기 |
| `core/attack.py` | 우선순위 힙 + 중립/사람 분기 + `tilesPerTickUsed` 예산 |
| `core/engine.py` | tick 10Hz. 타일 100 미만 수비자 흡수 규칙 |
| `ai/simple_ai.py` | 투입 비율 `병력/20`(봇). 상수 재조정 |
| `tests/` | `test_blocked_tile_goes_back_to_front_of_queue` **폐기**. 힙 순서 테스트로 교체 |

### 증강은 P7 까지 보류

`core/augments.py` 는 지우지 않고 그대로 둔다. 다만 **P1~P6 동안 엔진에서 떼어 둔다** —
코어가 흔들리는 동안 붙여 두면 무엇이 원본과 다른지 가려진다.

v0.1 에서 잰 증강 밸런스(개척단 우세, 할인 중첩 하한 도달률 등)는 **전부 무효다.**
코어 공식이 통째로 바뀌므로 그 위에서 잰 수치는 아무것도 말해 주지 않는다.

## 5.5 P1 진행 기록 (2026-08-21)

**P1a·P1b 완료.** 지도가 1,600칸 → **37,575~134,751칸**(원본 파일)으로 바뀌었고
공식이 전부 원본 값이 됐다. 테스트 42개.

### 실측

| | |
|---|---|
| 지도 적재 (world/asia/europe/africa) | 1~3ms |
| 지형 파싱 검증 | 육지 수가 4개 지도 모두 manifest 와 일치 |
| 한 판 (world, 4인, 900초) | **약 16초** — v0.1(0.5초)의 32배 |
| 증분 카운트 vs 전수 대조 | 일치 |

판당 16초라 240판이 64분이다. `--jobs` 로 프로세스를 나눈다(판끼리 독립).

### 상한 배율 — 지도 규모가 왜 중요한지 숫자로

1타일 대비 병력 상한:

| 타일 | 배율 |
|---|---|
| 1,600 (v0.1) | 2.6배 — 영토 확장이 거의 무의미 |
| 37,575 (World) | **11.9배** |
| 134,751 (Europe) | 21.5배 |

## 5.13 원본 봇 이식 — `ai/nation.py`

`NationExecution` + `AiAttackBehavior` 를 옮겼다. v0.1 의 `simple_ai` 와 근본이 다르다 —
그쪽은 "충전율이 넘으면 친다"였는데 원본은 **세 비율**로 판단한다.

| 비율 | 뜻 | 값 |
|---|---|---|
| `trigger_ratio` | 이만큼 차야 **공격을 고려**한다 | rand(50,60)% |
| `reserve_ratio` | 사람을 칠 때 **남겨 둘** 병력 | rand(30,40)% |
| `expand_ratio` | 중립을 먹을 때 남겨 둘 병력 | rand(10,20)% |

**핵심은 비대칭이다.** 중립은 10~20% 만 남기고 거의 전부 쏟고, 사람은 30~40% 를
남긴다. 빈 땅은 게걸스럽게, 사람은 여유가 있을 때만 — 이게 원본 봇의 성격이다.
둘을 같게 두면 초반 확장이 굼떠져 봇이 자라지 못한다.

그 밖에 옮긴 것:
- **반응 주기가 난이도별로 다르다**(`getAttackRate`): easy 6.5~10초, impossible 3~5초
- **표적은 병력이 적은 쪽부터**(원본이 오름차순 정렬)
- hard 이상만 `troopSendCap`(이웃 대비 75%/90% 유보)과 "상대 병력 20% 미만이면 안 친다"
- **구조물을 가진 봇**은 평소 여유를 안 기다리고 `expand_ratio` 로 친다 — 뺏긴 건물을
  되찾아야 하는데 봇이 그걸 지워 버리기 때문(원본 주석)

`play.py --ai nation|simple`, `--difficulty easy|medium|hard|impossible` 로 고른다.

### 실측 (world 4인, 클락 normal, seed 3)

| 난이도 | 결과 |
|---|---|
| easy | 정복 1821초 · 실행 38초 |
| impossible | 정복 2189초 · 실행 86초 |

**난이도가 높을수록 판이 길어진다** — 방향이 맞다. 실행 시간이 `simple_ai`(213초)보다
훨씬 짧은 것은 반응 주기가 10배 느리기 때문이다(65~100 tick vs 10 tick).

### 변이 4건 (전부 잡힘)

유보율 비대칭 제거 / `trigger_ratio` 검사 제거 / 반응 주기 무시 / hard 의 약한 공격 차단 제거.

⚠ 처음 두 번은 **패턴이 안 맞아 변이가 아예 적용되지 않았다**(줄바꿈 이스케이프).
"테스트가 통과했다"가 아니라 "변이가 안 들어갔다"였다 — 변이 스크립트는 패턴을 못
찾으면 **소리 내어 실패해야 한다.**

## 5.14 스폰 · 철도 — 마지막 두 조각

### 시작 영토는 1칸이 아니라 **반경 4의 원(49칸)**

`SpawnExecution` + `getSpawnTiles`. 1칸으로 시작하면 상한 공식(`타일^0.6`)의 바닥에서
출발해 초반이 지나치게 느리고, 첫 공격 한 번에 탈락할 수 있다.

- 원 안이 **하나라도** 바다·통행불가·남의 땅이면 **통째로 무른다.** 걸러서 주면
  해안에 반쯤 걸친 시작점이 생겨 시작 영토가 나라마다 달라진다
- 시작점끼리 맨해튼 거리 30 이상, 지도 가장자리 제외
- 1,000번까지 시도하되 **750번을 넘기면 거리 조건을 푼다** — 좁은 지도에서 영영
  못 뽑는 것을 막는 안전장치다

### 철도 — 남의 역에 닿는 것이 2.5배 벌린다

동맹 35,000 · 남/팀 25,000 · **자기 10,000**. 자기 건물끼리만 이어 골드를 찍는 것이
가장 안 벌린다. 그래서 철도를 깔면 이웃과 사이가 좋을 이유가 생긴다.
역은 따로 짓지 않고 **도시·항구·공장에 붙고**, 거리 15~110 안에서만 이어진다.

## 5.15 AI 경제에서 두 번 데었다

둘 다 **규칙 이식이 아니라 봇의 판단** 문제인데, 판에서 계통이 통째로 안 나타나게 만든다.

1. **"가장 비싼 것부터 산다" 는 방어초소가 무한 흡수구가 된다.** 초소는 25만에서
   비용 상한이라 그 뒤로 값이 안 오른다. 도시(50만~100만)를 못 사는 골드 구간에서
   초소만 계속 사서 한 판에 **41개**를 짓고, 공장·사일로가 0개였다 — 철도와 핵이
   판에서 아예 안 나왔다.
2. 가중 무작위로 바꾸니 공장이 생겨 **기차 293대**가 나왔지만 초소는 여전히 72개였다.
   비용 상한이 있는 종류에 **개수 상한**(영토 1,500칸당 1개 등)을 두고서야 균형이 잡혔다.

⚠ 그 개수 상한은 **원본 값이 아니라 우리가 정한 것**이다. 원본
`NationStructureBehavior` 를 옮기면 사라진다. `ai/nation.py` 에 그렇게 적어 뒀다.

### 최종 통합 실전 (world 4인, 클락 normal, medium, seed 5)

```
정복 2194초 · 생존 1 · 실행 35초
  상륙 33척 · 무역선 608척 · 전함 43척 · 기차 298대 · 초소 10개 · 공장 2개
  증분 카운트 = 전수 대조 ✅
```

**사일로는 여전히 0개다.** 봇이 900~2,200초에 버는 골드로는 100만에 못 닿는다.
핵은 테스트(발사·요격·폭발·낙진·건물 파괴)로만 검증돼 있고, 실전에서 나오려면
경제 규모가 원본 수준(전체 크기 지도·더 긴 판)이어야 한다.

## 5.16 UI — 실측이 설계를 정했다

`ui/frame.py`(프레임 생성) · `ui/map_widget.py` · `ui/hud.py` · `ui/main_window.py` ·
`ui/app.py`.

### 왜 타일 해상도인가

| 방식 | 500×250 지도 한 장 |
|---|---|
| 픽셀 해상도로 `np.repeat` 후 합성 (`render.py` 방식) | 69ms → **14.5 fps** |
| **타일 해상도로 만들고 확대는 Qt** | **4.0ms → 253 fps** |

17배 차이가 전부 픽셀 확대에서 나온다. 12만 타일을 scale 2 로 펼치면 50만 픽셀 ×
3채널을 매 프레임 만들고 자르고 형변환하는데, 그 일은 GPU 가 공짜로 해 준다.
지형 바닥은 한 번만 굽고(핵이 터질 때만 다시), 매 프레임 하는 일은 소유자 색 섞기뿐이다.

세 층: **지형+소유자**(QImage, Qt 가 확대) → **국경선**(`drawLines`) → **이름**(QPainter).

### 설계 5절 함정을 지킨 것

- 격자선 없음. **소유자가 다른 변에만** 선을 긋는다
- 확대에 `SmoothPixmapTransform` 을 **끈다**. 켜면 국경이 뭉개져 덩어리 경계가 흐려진다
- `WA_StyledBackground` 를 켜야 QWidget 서브클래스 배경이 칠해진다
- 라벨 크기는 **영토 덩어리의 실제 폭**에서 뽑는다
- 질감은 타일보다 큰 주기에서(`TEXTURE_PERIOD`) — 타일마다 뽑으면 체크무늬가 된다

### 새로 데인 것 둘

- **`QImage` 는 버퍼를 복사하지 않는다.** numpy 배열을 지역변수로만 두면 다음 프레임에
  회수돼 화면이 깨진다. `self._buf` 로 살려 두고 `ascontiguousarray` 로 넘긴다.
- **오프스크린 플랫폼은 시스템 폰트를 하나도 못 본다**(실측 `QFontDatabase.families()`
  = 0개). 글자가 전부 두부(□)로 나오는데 **UI 버그가 아니다** — 스크린샷을 보고
  폰트 버그로 오해해 한참 헤맸다. `--shot` 은 기본 플랫폼으로 찍고, 화면이 없는
  환경에서만 `--offscreen` 을 준다. 폰트가 0개면 경고를 찍는다.

### 조작

좌클릭 = 그 칸의 **소유자 전체**를 공격(원본과 같다). 육지로 못 닿으면 배로 간다.
우클릭 드래그 = 이동, 휠 = 커서 고정 확대, Space = 일시정지.

## 5.17 이식 대조 — 원본을 **실행해서** 맞춰 봤다

"코드를 눈으로 봤다"나 "테스트가 통과한다"는 이식이 맞다는 근거가 아니다. 근거는
**같은 입력에 같은 출력이 나오는가** 하나뿐이다.

Node 22+ 가 TypeScript 를 그대로 실행하므로, 원본 소스를 고치지 않고 함수를 부를 수
있다. `tools/oracle.mts` 가 원본을 실행해 기준값을 JSON 으로 뽑고,
`tools/verify_port.py` 가 같은 입력을 우리 Python 에 넣어 대조한다.
`tests/test_fidelity.py` 가 그 대조를 테스트로 돌린다.

```
✅ 181/181 항목이 원본 실행값과 일치
```

### 대조한 것

| 묶음 | 항목 |
|---|---|
| **전투** | `attackLogic` 사람 12케이스 · 중립 18케이스(지형 3종 × 병력 × 사람/봇) |
| | `attackTilesPerTick` 사람/중립 8케이스 |
| 병력 | `maxTroops`(사람/봇/도시) · `troopIncreaseRate` |
| 유닛 | 9종 × (비용 4단계 · 건설 tick · 체력) |
| 핵 | 반경 3종 · 속도 4종 · `nukeDeathFactor`(일반/MIRV) · `samRange` |
| 무역·철도 | `tradeShipGold` · `tradeShipSpawnRate` · `trainGold` · `trainSpawnRate` |
| 클락 | 요구 타일 4속도 × 14시점 + 팀전 |
| 스칼라 | 26개(초소·동맹·배신자·전함·기차·스폰 거리·`waterNukes` 등) |

### 실행 방법

```bash

./node_modules/.bin/tsx <이리포>/tools/oracle.mts <원본리포> > <이리포>/tests/oracle.json
python tools/verify_port.py tests/oracle.json
```

### 대조 자체를 변이로 검증했다

공격측 손실 계수 0.8→0.81 · 상한 지수 0.6→0.61 · 평야 mag 80→81 · 클락 천장
3500→3400 · 철도 동맹 수익 35,000→34,000 — **다섯 개 전부 잡혔다.**

### ⚠ 하네스가 틀렸던 것 하나

처음 돌렸을 때 클락만 5개 불일치였다. 원본이 "시간 × 0.35" 를 낸다는 말이 안 되는
값이라 하네스를 의심했고, 실제로 `doomsdayClockRequiredTiles(profile, land, elapsed)`
인데 `(profile, elapsed, land)` 로 넘기고 있었다. **불일치가 나오면 우리 구현을
고치기 전에 하네스를 먼저 의심한다.**

### 아직 대조 못 한 것 (정직하게)

기준값을 뽑으려면 Game/Player 를 크게 흉내 내야 하는 것들이다. 값이 아니라 **흐름**이라
단위 테스트로만 덮여 있다:

- `AttackExecution.tick()` 의 루프 순서와 우선순위 힙 공식
- `TransportShipExecution` 의 경로·도착 처리, `WarshipExecution` 의 표적 우선순위
- `SpawnExecution` 의 후보 탐색(반경 4 원·거리 30·750회 완화)
- 봇 판단(`AiAttackBehavior`) — 비율 범위는 대조했지만 결정 흐름은 아니다
- 폭발 타일 집합(`blast_tiles`) — 난수가 들어가 값 대조가 안 된다

## 5.18 해상도를 올렸다 — 4.5절의 왜곡이 대부분 사라진다

원본은 같은 지도를 세 크기로 굽는다. 셋 다 담고 **기본을 `map4x`** 로 올렸다.

| 크기 | world | 육지 | 프레임+시뮬 |
|---|---|---|---|
| `map16x` | 500×250 | 37,575 | 11.5ms (87fps) |
| **`map4x`** (기본) | 1000×500 | **158,068** | 32.0ms (**31fps**) |
| `map` | 2000×1000 | 651,569 | 57.3ms (17fps) |

`map4x` 는 육지가 4.2배라 **`DEFENSE_DEBUFF_MIDPOINT`(15만)와 `largeAttackBonus`
문턱(10만)이 드디어 발동하는 범위**에 들어온다. 4.5절에 적어 둔 "작은 지도에서는
죽은 가지" 문제가 여기서 대부분 풀린다. 핵 반경의 상대 비중도 4배 정확해진다.

### 렌더러를 다시 짰다 (2차 실측)

| | 1000×500 | 2000×1000 |
|---|---|---|
| 매 프레임 지형+소유자 float 블렌드 | 16.2ms (62fps) | 59.6ms (**17fps**) |
| **소유자 RGBA 오버레이만** | 4.4ms (227fps) | 17.2ms (**58fps**) |

지형은 판 내내 안 바뀌니 **한 번만 굽고**, 매 프레임 하는 일은 `owner` 배열을 RGBA 로
조회하는 uint8 gather 하나다. 합성은 Qt 가 알파로 한다. 국경 계산에는 **뷰포트 컬링**을
넣었다 — 원본 크기에서 전체를 훑으면 18ms 다.

### ⚠ git 이 지도 파일 하나를 조용히 깨뜨렸다

`core.autocrlf=true` 인 환경에서 git 이 **`europe/map.bin` 을 텍스트로 오판해**
LF→CRLF 변환을 했다. 4,855,488 → 4,855,502 바이트(14바이트 증가)가 되어 manifest 의
width×height 와 안 맞아 적재가 실패했다. **다른 11개 지도는 멀쩡했다** — 그 파일에만
LF 로 보이는 바이트가 있었기 때문이다. 한 파일만, 조용히 깨진다.

→ `.gitattributes` 에 `*.bin binary` 를 박고, 깨진 파일은 원본 git blob 에서
`core.autocrlf=false` 로 다시 꺼냈다. 지도 12개 전부 manifest 와 일치하는 것을
테스트로 못 박았다(`test_land_count_matches_manifest` 가 세 크기를 전부 돈다).

## 5.19 조작성

원본에서 클릭은 **그 칸이 아니라 소유자 전체**를 겨눈다. 그래서 "지금 무엇을 치게
되는가"가 안 보이면 클릭이 도박이 된다. 그 자리를 셋으로 메웠다.

- **호버 강조** — 커서가 얹힌 나라의 국경만 밝게 덧그린다. 대상이 눈에 보인다
- **대상 정보** — 그 나라의 병력·영토와 함께 **상대/내가 보낼 병력** 비를 띄운다.
  원본 공식의 핵심이 `within(수비병력/공격병력, 0.6, 2)` 이라 이 값이 판단의 전부다.
  0.6 아래면 유리, 2 위면 불리라고 그대로 적어 준다
- **클릭 표시(ping)** — 누른 자리에 파문을 남긴다. 아무 일도 안 일어나면 눌렸는지조차
  알 수 없었다. 닿지 않는 곳이면 이유를 배너로 알려 준다

그 밖에: WASD/화살표 이동 · `+`/`-` 확대 · `F` 화면 맞추기 · `H` 도움말.
확대 범위를 0.2~24 로 넓혔다 — 원본 크기 지도(2000×1000)를 화면에 담으려면
하한 0.5 로는 모자랐다.

## 5.20 가로 순환 · LOD · 부드러운 카메라

### 가로로 순환한다

오른쪽으로 계속 가면 왼쪽이 나온다. 지도를 화면이 덮일 만큼 좌우로 반복해 그리고,
클릭 좌표는 지도 폭으로 나머지를 취한다.

⚠ **화면만 순환한다. 게임 규칙은 순환하지 않는다.** 원본 `neighbors4` 가 x 경계를
넘지 않으므로 지도 양 끝은 실제로 안 이어져 있다 — 그 사이는 태평양이라 육지가
맞닿지 않아 눈에 띄지 않는다. 규칙까지 순환시키면 이식이 깨진다.
`test_map_wraps_horizontally_on_screen_only` 가 양쪽을 다 못 박는다.

### 카메라를 게임 tick 에서 떼어냈다

게임은 10Hz(원본 `turnIntervalMs`)인데 카메라를 거기 얹으면 이동이 뚝뚝 끊긴다.
카메라·화면 갱신은 **별도 60Hz 타이머**로 돌리고, 눌린 키에서 목표 속도를 만들어
현재 속도를 그쪽으로 당긴다(가속·감속). 누른 순간 튀지 않고 뗀 순간 멈추지도 않는
그 사이가 '부드럽다'는 느낌을 만든다.

### 해상도와 성능 (진행 중인 판, 1600×900 창)

| | 줌 아웃 | 2배 | 6배 |
|---|---|---|---|
| **`map4x`** (기본, 1000×500) | 71fps | 83fps | 104fps |
| `map` (2000×1000) | 13fps | 36fps | 13fps |

`map` 은 **렌더링이 아니라 시뮬레이션이 무겁다**(map4x 3.4ms/tick vs map 14.2ms/tick).
쓸 수는 있지만 기본은 `map4x` 다.

### ⚠ 성능을 세 번 헛짚었다 — 측정 조건을 안 봤기 때문

"2배 확대에서 6fps" 를 쫓다가 **국경선 그리기**를 의심했고(국경이 0개인 판이었다),
다음엔 **라벨 계산**을 의심했고(캐시해도 안 변했다), 그 다음에야 원인을 알았다:
**앞선 측정 세 번이 전부 게임이 이미 끝난 상태를 재고 있었다.** `st.tick()` 은
`if self.over: return` 로 즉시 반환하므로 시뮬레이션 비용이 0 으로 나왔고, 그래서
남은 시간이 어디서 오는지 계속 안 맞았다.

진행 중인 판에서 다시 재니 그림이 바로 맞았다. **측정값을 믿기 전에 무엇을 재고
있는지부터 본다** — 판이 끝났는지, 공격이 진행 중인지, 국경이 있는지.

그 과정에서 얻은 진짜 개선 둘은 남겼다: 오버레이를 **보이는 줄만** 만들고,
라벨은 1초에 한 번만 다시 잡는다(원본 크기에서 12~14ms).

## 5.21 원본 크기를 쓸 만하게 — AI 두 함수가 전부였다

"원본 크기(2000×1000, 육지 65만)로 하려면?" 을 cProfile 로 재니 답이 한눈에 나왔다.
**게임 규칙이 아니라 AI 가 부르는 두 함수**가 전부였다:

| 함수 | 호출당 | 원인 |
|---|---|---|
| `border_targets` | **119ms** | 내 타일마다 `neighbors()` — 영토 17만 칸이면 68만 번 루프 |
| `shoreline_tiles` | **589ms** | 내 타일마다 `is_shore()` — 그 안에서 또 이웃 순회 |
| `_advance_attacks`(규칙) | 1.1ms | — |

둘 다 numpy 로 폈다. 배열을 네 방향으로 밀어 한 번에 본다.

```
시뮬레이션  14.2ms/tick → 1.7ms/tick   (원본 크기, 8배)
             3.4ms/tick → 0.6ms/tick   (map4x)
```

**빨라져도 답이 다르면 소용없다.** 두 지도 크기 × 두 시드 × 전 플레이어로 옛 구현과
결과가 완전히 같은 것을 확인하고, 그 대조를 회귀 테스트 7개로 고정했다.

### LOD 문턱도 틀려 있었다

`round(1/zoom)` 을 쓰는 바람에 줌 0.8 에서 stride 1 이 나왔다(`round(1.25)=1`) —
축소해서 보는데 원본 해상도로 뽑고 있었다. `ceil` 로 바꾸니 **화면 픽셀 하나당 표본
하나**가 된다.

### 현재 성능 (진행 중인 판, 1600×900 창)

| 줌 | `map4x` (기본) | `map` (원본 크기) |
|---|---|---|
| 전체보기 | 78fps | 24fps |
| 2배 | 81fps | 37fps |
| 6배 | 119fps | 92fps |

원본 크기는 **축소할수록 느려진다** — 지도가 화면보다 작아지면 순환 사본을 여러 벌
그리기 때문이다. 그게 순환의 대가다. 확대해서 보는 동안은 92fps 까지 나온다.

## 5.22 게임으로 만들기 — 조작 계층

"이게 시뮬레이션이야?" 라는 지적이 맞았다. 규칙은 181/181 원본과 일치하는데
**사람이 할 수 있는 게 클릭 공격 하나뿐**이었다. 골드는 쌓이는데 쓸 방법이 없고,
건물·배·핵이 지도에 그려지지도 않았다.

### 원본 클라이언트를 확인했다

서버 쪽 규칙만 읽고 클라이언트를 안 봤던 게 원인이다. `src/client/hud/layers/` 에
37개 레이어가 있고, 우리가 만든 것과 대조하면:

| 원본 | 우리 |
|---|---|
| `MainRadialMenu` / `RadialMenu` / `RadialMenuElements` | ✅ `ui/radial.py` + `ui/actions.py` |
| `BuildMenu` (건설 10종) | ✅ 건설 하위 메뉴 |
| `PlayerActionHandler` / `SendResourceModal` | ✅ 외교 하위 메뉴 |
| `StructurePass` / `StructureLevelPass` / `UnitPass` | ✅ `_draw_units` |
| `EventsDisplay` · `AlertFrame` · `AttacksDisplay` | ⬜ |
| `ChatDisplay` · `EmojiTable` · `PlayerPanel` | ⬜ |
| `AllianceClusters` · `AttackRings` · `NukeTelegraphs` | ⬜ |

**조작 방식이 달랐다.** 원본은 타일을 클릭하면 방사형 메뉴가 뜬다. 우리가 만든
"좌클릭 = 즉시 공격" 으로는 골드도 못 쓰고 외교도 못 한다.

### 넣은 것

- **유닛 렌더링** — 건물은 모양으로(◉도시 ⚓항구 ▦공장 ◈초소 ▲사일로 ◮SAM),
  배·전함·무역선·핵은 점으로. 색은 이미 소유자를 뜻하므로 색으로 종류까지 나타내지
  않는다. 건물은 확대했을 때만 그린다(축소 상태에서 점을 뿌리면 지저분하다)
- **방사형 메뉴** — 공격(+핵 3종) · 건설(7종) · 상륙 · 외교(6종)
- **못 하는 항목은 지우지 않고 회색으로 남긴다.** 원본도 `disabled` 로 그렇게 한다 —
  "왜 안 되지"를 알려면 항목이 보이면서 이유가 붙어야 한다.
  `사일로가 없다` · `골드 125,000 필요 (보유 40,000)` · `⚠ 배신자가 된다` 처럼

### ⚠ 이식 누락을 하나 잡았다 — MIRV 비용

`UNIT_INFO` 에 **MIRV 가 통째로 빠져 있었다.** 계획서 3절 표에는 적어 뒀는데 코드에
안 넣었고, 아무도 MIRV 를 살 수 없으니 드러나지 않았다. 메뉴를 만들면서 `KeyError` 로
터져서 알았다.

원본은 `25e6 + 판전체발사수 × 15e6` 인데, **그 수가 플레이어가 아니라 게임에 있다**
(`game.stats().numMirvsLaunched()`). 다른 유닛은 전부 보유량 기준이라 `UnitStore` 만
보면 되는데 MIRV 만 예외다 — `GameState.mirvs_launched` 를 두고 `nuke_cost()` 가 넘긴다.

**UI 를 만들다 규칙 버그가 나왔다.** 아무도 안 쓰는 경로는 테스트가 있어도 안 드러난다.

### §5.23 소식·경보 — 무슨 일이 일어났는지 보이게

원본은 `MessageType` 22종을 카테고리(공격·외교·핵·무역·잡)로 나눠 로그에 쌓고, 급한
것은 화면 가운데 위에 띄운다. `core/events.py` 에 그대로 옮겼다.

- `EventLog(limit=400)` — 오래된 것부터 버린다. 원본도 무한히 쌓지 않는다
- `recent(who, ...)` 는 **나와 상관있는 것만** 준다. 남의 판을 다 보여주면 내 일이 묻힌다
- `urgent_for(who, since_tick)` → 화면 가운데 경보. 핵·동맹 파기·탈락처럼 놓치면
  안 되는 것만(`URGENT`)
- 엔진 16곳에서 `emit()` 한다 — 공격·상륙·핵·SAM·격추·정복·점령·동맹 4종·기부 2종·격침

**"전투" 패널은 로그가 아니다.** 진행 중인 공격의 *현재 상태*(남은 병력·목표)를 보여
준다. 로그로 대신하면 "지금 어떻게 되고 있는지"를 알 수 없다.

### ⚠ 이식 누락 둘 — 스폰 면역

사람(P0)을 가만히 두고 켰더니 **155초 만에 탈락**했다. 원본에는 시작 직후 봐주는
구간이 있는데(`Config.ts :: spawnImmunityDuration()` = `5 * 10` tick = 5초) 통째로
빠져 있었다.

규칙이 **비대칭**인 것이 핵심이다. `PlayerImpl.canAttackPlayer()` 원본 주석 그대로:

> Only human attackers respect PVP immunity

즉 봇·Nation 은 면역 중인 상대도 친다. 대칭으로 만들면 시작 5초 동안 판이 통째로
멈춘다 — 돌연변이로 확인했다(`test_bots_and_nations_ignore_immunity` 가 잡는다).
봇은 `isImmune()` 자체가 false 라 표적으로서도 면역이 없다.

`can_attack(pid, target)` 한 곳에 모아 `launch_attack` 과 `send_boat` 가 같이 쓴다.
**상륙에도 걸어야 한다** — 공격만 막으면 배로 그냥 뚫린다.

⚠ 이 이식으로 기존 테스트 3개가 깨졌다. 헬퍼들이 `tick_count=0` 에서 시작하고 있어서
전원이 면역 상태였다. 의도한 동작이라 헬퍼를 면역 뒤로 옮겼는데, `test_naval` 의
무역 테스트는 `tick_count * GOLD_PER_TICK` 으로 기준선을 빼고 있어 **0 에서 시작한다는
가정이 숨어 있었다.** 절대 tick 이 아니라 경과분으로 고쳤다.

⚠ 상륙 면역 테스트를 처음에는 전부 육지인 지도에서 짰다. `send_boat` 가 면역이 아니라
`best_spawn` 실패로 `None` 을 돌려주고 있어서 **배선을 되돌려도 통과했다.** 보호
장치를 재는 테스트는 "막지 않았으면 성공했을 것"을 먼저 단언해야 한다 — 지금은
면역 밖에서 같은 상륙이 뜨는 것을 확인한 뒤 면역 안에서 막히는지 잰다.

### §5.24 공격 비율과 면역 바 — HUD 대조

원본 HUD 는 `src/client/hud/layers/` 아래 36개다. 게임 조작에 직접 걸리는 것만 골라
대조했더니 두 곳이 비어 있었다.

**공격 비율.** 슬라이더 자체는 있었지만 **키로 못 움직였고 몇 명이 가는지 안 보였다.**
원본 값(`ControlPanel.ts` · `UserSettings.ts`):

| 항목 | 값 | 출처 |
|---|---|---|
| 기본 | 20% | `attackRatio()` 기본 `0.2` |
| 범위 | 1–100% | 슬라이더 `min="1" max="100"` |
| 증분 | 10%p | `attackRatioIncrement` 기본 `10` |
| 키 | T 내림 / Y 올림 | `defaultKeybinds` |
| 스냅 | 1% 에서 올리면 11% 가 아니라 10% | 원본 주석: "to keep a consistency" |

% 옆에 실제 병력 수를 같이 쓴다 — % 만 보여주면 그게 몇 명인지 모른다.

**면역 바.** `ImmunityTimer.ts` 는 화면 맨 위 7px 진행바다. 면역을 규칙에만 넣고
화면에 안 보이면 공격이 왜 거부되는지 알 방법이 없다 — 방사형 메뉴의 회색 항목은
타일을 눌러야 보이지만 이건 항상 보인다.

⚠ **하한 방어가 죽은 코드였다.** `nudge_ratio` 안에서 `max(ATTACK_RATIO_MIN, ...)`
로 막고 있었는데, 돌연변이로 그 줄을 지워도 테스트가 통과했다. `QSlider.setValue` 가
이미 범위로 클램프하기 때문이다. 테스트를 의심하기 전에 돌연변이를 의심하라는
규칙의 반대 경우 — **여기서는 돌연변이가 맞았고 코드가 중복이었다.** 죽은 줄을 지우고
슬라이더 범위를 상수에서 끌어오게 바꾸니 같은 돌연변이가 잡힌다.

### ⚠ 이식 누락 셋 — 관계도가 통째로 없었다

가장 큰 누락이다. **UI 가 아니라 규칙**이다: 원본 AI 는 관계 값으로 누구를 칠지·
동맹 요청을 받을지·금수를 걸지 정한다. 없을 때 우리 AI 는 동맹 요청을 **동전
던지기**로 받고 있었다 — 방금 나를 핵으로 친 상대와도 절반 확률로 손을 잡는다는
뜻이고, 그러면 사람이 외교를 관리할 이유가 사라진다.

`core/relations.py` 로 옮겼다. 값은 **한 방향**이다 — 내가 너를 보는 눈과 네가 나를
보는 눈이 다르다. 이게 핵심이라 양방향으로 만들면 안 된다: 공격당한 쪽만 나빠지고
친 쪽은 그대로여야 공세가 이어진다.

| 값 | 문턱 | 출처 |
|---|---|---|
| 범위 | −100 ~ +100, 기본 0 | `updateRelation` 의 `within` |
| 적대 / 불신 / 중립 / 우호 | < −50 / < 0 / < 50 / ≥ 50 | `relationFromValue` |
| 감쇠 | 매 tick 0.05 씩 0 으로, ±0.1 안에서는 0 으로 붙임 | `decayRelations` |

무엇이 얼마나 움직이는가(각 Execution 에 흩어져 있던 것을 `constants.py` 에 모았다):

| 사건 | 변화 | 방향 |
|---|---|---|
| 공격 | −60 / −70 / −80 / −100 (난이도순) | 맞은 쪽만 |
| 동맹 성사 | +100 | **양쪽** |
| 동맹 파기 | −100 | 당한 쪽 |
| 〃 이웃이 목격 | −40 | 배신자의 국경 이웃 전부 |
| 핵 | −100 | 맞은 쪽만 |
| MIRV | −100 | **양쪽** — 쏜 쪽도 상대를 적으로 확정한다 |
| 병력 기부 | +50 (액수 무관) | 받은 쪽 |
| 골드 기부 | 덩어리당 +5, 최대 100 | 받은 쪽 |
| 금수 | −20 (풀면 +20) | 걸린 쪽이 건 쪽을 |

**골드 기부의 덩어리 크기가 시간에 따라 커진다** (`chunk + chunk × tick/(3000+100)`).
안 그러면 후반에 남아도는 골드로 관계를 살 수 있다.

⚠ **금수는 한 번만 깎는다.** 걸려 있는 동안 매 tick 깎으면 몇 초 만에 −100 에 박혀
풀어도 회복이 안 된다. 원본은 적용 여부를 따로 기억한다(`embargoMalusApplied`).

⚠ **동맹 파기 이웃 필터를 잘못 읽었다.** 처음에 "피해자 제외"로 썼는데 원본은
`!n.isOnSameTeam(recipient)` 다 — **피해자 본인이 이웃이면 −40 이 더 얹힌다.**
clamp 가 update 마다 걸리므로 최종값은 (동맹 +100) −100 −40 = −40 이다.

AI 배선(`ai/nation.py`): 동맹 수락은 중립 미만이면 거절 · 우호면 2/3 확률로 수락 ·
중립은 반반. 금수는 **거는 문턱(적대)과 푸는 문턱(중립)이 다르다** — 같으면 관계가
문턱 근처에서 떨릴 때 매 tick 켜졌다 꺼진다. hard 는 중립으로 안 풀고 impossible 은
우호가 돼도 안 푼다.

실전 스모크(6국 300초, map4x): 우호 0 → 8 → 0, 적대 2 유지, 동맹 4 성사. 값이
고여 있지 않고 실제로 오르내린다.

⚠ **돌연변이 하나가 무효였다.** 금수 재적용 돌연변이를 `applied.discard()` 추가로
만들었는데 바로 다음 줄의 `applied.add()` 가 상쇄해 아무 일도 안 했다. 통과를
보고 테스트를 의심했지만 **돌연변이가 틀린 쪽이었다** — `add` 를 지우니 잡힌다.

### §5.25 관계를 화면에 — 어느 쪽 값을 보여줄 것인가

관계도를 규칙에만 넣으면 사람은 AI 가 왜 동맹을 거절했는지 알 수 없다.
호버 정보와 외교 메뉴 두 곳에 붙였다.

**중요한 건 방향이다.** 보여줘야 하는 것은 *상대가 나를 보는 값*이지 내가 상대를
보는 값이 아니다 — 동맹 요청이 받아들여질지 정하는 것은 상대 쪽이기 때문이다.
돌연변이로 방향을 뒤집으면 테스트가 잡는다.

등급 이름·색은 `relations.py` 한 곳에만 둔다(`RELATION_LABEL`/`RELATION_COLOUR`).
UI 여러 곳에 흩어지면 문턱을 바꿀 때 화면과 규칙이 어긋난다.

⚠ **오프스크린 캡처의 글자는 전부 두부(□)로 나온다.** `QT_QPA_PLATFORM=offscreen`
환경에서 `QFontDatabase.families()` 가 **0개**다. 렌더 버그가 아니라 캡처 환경의
한계이므로, 스크린샷으로 글자를 검증하지 말고 위젯의 `text()` 를 직접 읽어 확인한다.

⚠ **소식 패널이 안 뜨는 것이 정상일 때가 있다.** 90초 스모크에서 비어 있길래
버그를 의심했는데, 로그 전체가 AI 끼리의 동맹 11건이었고 `who=0` 인 이벤트가
하나도 없었다. `recent(who=me)` 는 **나와 상관있는 것만** 주므로 맞는 동작이다.

### ⚠ 이식 누락 넷 — 이모지는 장식이 아니다

원본에서 이모지는 **관계 조작 수단**이다. 🖕 하나가 상대 관계를 −100 움직인다 —
사람이 AI 의 눈을 바꾸는 방법 중 **유일하게 공짜**다(공격은 병력을, 기부는 골드를
쓴다). 그래서 5초 쿨다운이 붙어 있다.

| 이모지 | 관계 | 비고 |
|---|---|---|
| 🖕 | −100 | 돌이키기 어렵다 |
| 🤡 | −10 | |
| 🕊️ 🏳️ ❤️ 🥰 👏 | +15 | **easy 에서만.** 아니면 쿨다운마다 눌러 관계를 산다 |
| 나머지 55개 | 0 | 그냥 말이다 |

**AI 는 사람에게만 말을 건다**(`shouldSendEmoji` : 받는 쪽이 Human 이 아니면 false,
봇은 아예 안 보냄). AI 끼리 주고받지 않으므로 **화면에 뜨는 이모지는 전부 나에게 온
말**이다 — 이게 없으면 로그가 남의 대화로 덮여 내 소식이 묻힌다.

쿨다운이 **둘**이다. 섞으면 안 된다:

- `emojiMessageCooldown` 5초 — 같은 상대에게 도배 금지 (사람·AI 공통)
- `shouldSendEmoji` 30초 — **AI 가 먼저** 거는 말의 주기

⚠ 30초 쪽은 **확인과 기록을 한 함수에서 같이 한다**(`ai_may_speak`). 나눠 두면
호출부가 기록을 잊어 제한이 조용히 사라진다 — 돌연변이 E 가 이걸 잡는다.

AI 가 말하는 자리: 공격 직전(관계가 나쁘지 않으면 😈 선제, 나쁘면 😡 보복) · 핵 발사
(☢️💥) · 동맹 수락(🤝) · 거절(❓🤡) · 기부 답례(액수에 따라 ❤️ / 👍 / 🥱).
**적으면 적다고 말한다** — 답이 없으면 준 사람은 통했는지 알 수 없다.

### ⚠ 이식 누락 다섯 — 배신자는 90% 거절

이모지를 배선하다 같이 나왔다. 원본 `NationAllianceBehavior` 는 관계를 보기 **전에**
배신자 낙인을 먼저 본다(`nextInt(0, 100) >= 10` → 90% 거절). 관계만 보면 방금 남을
배신한 자가 "관계가 중립"이라는 이유로 받아들여져 배신에 비용이 없어진다.

실전 스모크(5국 map4x): AI 가 공격 전 😈 를 보냈고, AI 끼리는 0건이었다.

### §5.26 판이 끝났을 때 · 내가 죽었을 때

`WinModal.ts` 를 옮겼다. 지금까지는 배너 한 줄뿐이라 **사람이 죽은 줄도 몰랐다** —
가만히 두면 79초에 탈락하는데 화면에 아무 변화가 없었다(실측).

원본이 하는 두 가지가 핵심이다:

1. **탈락은 판이 안 끝나도 그 자리에서 뜬다**(`hasShownDeathModal`). 끝날 때까지
   기다리면 언제 죽었는지 알 수 없다.
2. **닫으면 관전이 이어진다.** 원본도 죽은 뒤 판을 계속 볼 수 있다.

⚠ 두 화면 모두 **판마다 한 번만** 떠야 한다. 조건(`st.over`)만 보고 매 tick 띄우면
닫아도 다음 프레임에 다시 떠서 관전이 불가능하다 — 처음에 이렇게 짰다가 돌연변이
A·B 로 잡았다. 탈락 화면을 봤다고 종료 화면까지 건너뛰면 안 되므로 플래그는 둘이다.

통계 열은 `StatsConstants.ts :: COLUMN_IDS` 중 우리가 셀 수 있는 것만 골랐다
(순위·나라·영토·병력·골드·도시·항구·사일로·동맹·배신). **배신 수는 판이 끝난 뒤
되짚어 보는 값**이라 여기 말고는 쓸 자리가 없다 — 안 세면 낙인이 흔적을 안 남긴다.

### ⚠ 이식 누락 여섯 — 스폰 페이즈

원본은 판이 시작되기 전에 **사람이 시작 위치를 고른다.** 그 동안 판 전체가 멈춘다 —
`activeDuringSpawnPhase()` 가 false 인 Execution 을 전부 건너뛰므로 AI 도, 공격도,
성장도 안 돈다. 우리는 자동 배정 후 바로 시작하고 있었다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 상한 | 100 tick (싱글플레이) | `numSpawnPhaseTurns()` |
| 시작 영토 | 중심 반경 4 원 = 49칸 | `getSpawnTiles` |
| 재배치 | 페이즈 동안 몇 번이든 | `SpawnExecution` — 옮길 때 `relinquish` |
| 종료 | **고르는 순간**(싱글플레이) | `SpawnExecution` 마지막 분기 |

⚠ **옮길 때 옛 자리를 반납해야 한다.** 빼면 고른 자리마다 영토가 쌓여 고르는 것만으로
이길 수 있다.

⚠ **페이즈가 끝날 때 시계를 0 으로 돌린다.** 안 그러면 고르는 데 쓴 시간이 스폰
면역에서 깎여 늦게 고른 사람일수록 보호를 덜 받는다. 원본은 면역 끝을
`spawnPhaseTurns + immunityDuration` 으로 더해서 같은 문제를 피한다.

**우리 값 하나**: `SPAWN_MIN_TILES = 20`. 원본은 사람이 고를 때 못 쓰는 칸을
걸러만 주는데, 그러면 반도 끝 세 칸을 골라도 시작이 돼 첫 공격에 사라진다.

⚠ **문턱 테스트가 문턱을 안 재고 있었다.** "전부 남의 땅"을 고르는 테스트는 유효
칸이 **0개**라 `not tiles` 에서 걸린다 — 20 이라는 문턱을 지워도 통과했다. 유효
칸이 1~19개인 조각을 만들고 **"빈 자리가 아니다"를 먼저 단언**하도록 고쳤다.

실전 확인(실제 창, 클릭 경로 전부): 안내 표시 → 40틱 영토 변화 0 → 클릭 시 49칸
확보·시계 0 재시작·면역 시작 → 이후 정상 진행.

### ⚠ 이식 누락 일곱 — 지도가 텅 비어 있었다

가장 크게 어긋나 있던 것. 원본 싱글플레이 기본 구성은 **72개 나라 + 봇 400개 = 472명**
이다(`SinglePlayerModal :: DEFAULT_OPTIONS.bots = 400`). 우리는 4~6명이었다 —
같은 규칙, 같은 지도인데 **전혀 다른 게임**이 된다.

**나라는 이름과 자리가 정해져 있다.** manifest 의 `nations` 에 실제 국가명과 좌표가
들어 있다(world = 72개). 좌표는 **원본 해상도(2000×1000) 기준**이라 축소본에서는
나눠야 한다 — `nation_coord_space` 로 어느 기준인지 파일에 남겼다.

⚠ **그 변환을 재는 테스트가 자기 자신과 비교하고 있었다.** 기대값을 `gm.nations`
에서 가져왔는데 그게 검사 대상과 같은 변환을 거친 값이라, 해상도를 안 나누는
돌연변이가 그대로 통과했다. manifest 원본 좌표에서 직접 계산하도록 고쳤다.

**Tribe(봇)는 Nation 과 다른 AI 다**(`TribeExecution.ts`):

| | Nation | Tribe(봇) |
|---|---|---|
| 동맹 요청 | 관계·배신자를 따진다 | **전부 받는다** |
| 건물 | 짓는다 | **하나씩 지운다**(10 tick 간격) |
| 표적 | 약한 이웃부터 | **배신자 우선**(동맹이어도 깨고 친다), 아니면 무작위 |
| 나라·사람 | 우선 노린다 | **절반 확률로 건너뛴다** |
| 첫 판단 | 문턱을 지킨다 | **무조건 중립으로 나간다** |
| 반응 주기 | 45~100 tick | 40~80 tick |

봇이 동맹을 다 받아 주는 것이 이 게임의 초반 구조다 — 사람은 주변 봇을 우방으로
묶어 두고 나라와 싸운다. 봇도 관계를 따지게 만들면 그게 사라진다.

**성능**: 472명 = 배치 0.7초 · **41.7 ms/tick**(10Hz 예산의 42%). 120명 8.6ms,
240명 14.8ms. 규모를 키워도 예산 안이라 원본 기본값을 그대로 쓴다.

### §5.27 규모가 커지자 UI 세 곳이 무너졌다

472명은 규칙만의 문제가 아니었다. 캡처해 보니 화면이 글자로 덮여 아무것도 안 읽혔다.

1. **지도 이름** — 폰트 크기를 영토 폭에서 뽑되 `max(9, …)` 하한이 있어, 아무리
   작아도 9px 로 그렸다. 원본은 하한이 아니라 **컷**이다: 화면상 크기가
   `cullThreshold`(0.008) 미만이면 정점을 죽여 아예 안 그린다
   (`name.vert.glsl`). 커서가 얹힌 나라만 예외(`isHighlighted`).
2. **순위표** — 줄 수를 플레이어 수로 잡아 472줄이 화면 왼쪽을 덮었다. 12줄로
   자르되 **마지막 한 줄은 상위권 밖일 때 내 자리**로 쓴다. 등수는 줄 번호가
   아니라 진짜 순위여야 한다 — 꼴찌인데 12등으로 적히면 거짓말이다.
3. **종료 화면** — 같은 문제. 15줄 + 내 줄.

⚠ **또 죽은 코드를 하나 지웠다.** 순위표에서 남는 줄을 비우는 코드가 돌연변이로
안 잡혔다 — `QLabel` 초기값이 이미 빈 문자열이고 `st.players` 는 판 중에 줄지 않아
그 방어에 도달할 경로가 없었다. `ATTACK_RATIO_MIN` 때와 같은 경우다.

### ⚠ 이식 누락 여덟 — 낮은 난이도는 사람을 봐준다

"방치하면 왜 이렇게 빨리 죽나"를 확인하다 나왔다. 원본 `AiAttackBehavior.shouldAttack`
은 **사람을 칠지 말지를 난이도로 거른다**:

| 난이도 | 사람을 치는 비율 | 원본 |
|---|---|---|
| easy | **1/4** | `nextInt(0, 4) !== 0` 이면 거절 |
| medium | 3/4 | `chance(4)` 면 거절 (`chance(n)` = 1/n) |
| hard · impossible | 전부 | 봐주지 않는다 |

**중립·나라·봇은 언제나 친다.** 사람만 걸러진다 — 안 그러면 AI 끼리 판이 멈춘다.
**배신자는 난이도와 무관하게 친다.** 낙인이 붙은 동안은 사람도 예외가 아니다.

같은 검사가 **핵에도 걸린다**(`NationNukeBehavior` 가 `shouldAttack` 을 먼저 본다).
없으면 easy 에서 사람을 안 치면서 핵만 떨구는 이상한 AI 가 된다.

⚠ **두 겹으로 어긋나 있었다.** 봐주기가 아예 없었던 데다, **우리 기본 난이도가
medium** 이었다 — 원본 싱글 기본은 `easy` 다(`DEFAULT_OPTIONS.selectedDifficulty`).
둘을 합치면 사람이 원본보다 **네 배 자주** 맞고 있었다.

⚠ 난이도별 비율을 각각 재는 테스트만 두면 **easy 와 medium 이 뒤바뀌어도 통과한다**
(각자 자기 값을 확인할 뿐이다). `easy < medium < hard` 순서를 따로 단언한다.

### ⚠ 이식 누락 아홉 — 표적 지정(동맹에게 부탁하기)

`REL_TARGETED = -40` 상수만 옮겨 두고 기능이 없었다. **이게 동맹의 실질적 효용이다**
— 없으면 동맹은 "서로 안 친다"는 소극적 약속일 뿐이고, 함께 싸우는 수단이 하나도
없다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 표적으로 남는 시간 | 10초 | `targetDuration()` |
| 다음 표적까지 | 15초 | `targetCooldown()` |
| 찍힌 쪽의 관계 | −40 | `TargetPlayerExecution` |
| 도와준 대가 | −20 (도운 쪽 → 부탁한 쪽) | `assistAllies` |

동맹은 **우호(FRIENDLY)일 때만** 도와준다. 거절할 때도 말을 남긴다 — 사이가 덜
좋으면 🥱, 표적이 나면 🥺, 표적이 내 동맹이면 🕊️. 왜 안 도와주는지 모르면 사람은
동맹을 관리할 수 없다.

⚠ **지속(10초)보다 쿨다운(15초)이 길다.** 만료됐다고 기록을 지우면 12초째에 또
찍을 수 있게 된다 — 같은 기록을 두 용도로 쓰므로 쿨다운 기준으로 지운다.

⚠ **지원은 중립 확장보다 먼저 본다.** 뒤에 두면 부탁이 10초 안에 만료돼 아무도
안 도와준다.

⚠ **테스트에서 `diplomacy.form()` 을 직접 부르면 안 된다.** 관계 +100 은
`accept_alliance` 에 붙어 있어서, form 만 쓰면 "동맹인데 사이는 중립"이라는 실제로는
안 나오는 상태가 된다 — 지원 테스트 네 개가 통째로 빗나갔다. `request` → `accept`
경로를 쓴다.

### §5.28 "방치하면 왜 빨리 죽나" — 원인을 갈라서 쟀다

같은 시드·같은 자리로 세 조건을 돌렸다(30나라 + 봇 120, map4x, 시드 5개):

| 조건 | easy | medium | hard |
|---|---|---|---|
| A 사람 · 조작 없음 | 102초 | 90초 | 72초 |
| B 나라 · 조작 없음 | 96초 | 98초 | 57초 |
| C 나라 · **AI 조작** | **477초** | **600초**(상한) | **600초**(상한) |
| A/B | 1.05 | 0.92 | 1.27 |

**세 난이도 모두 A ≈ B 다.** 사람이라서 표적이 되는 것이 아니다 — 조작만 하면
5~8배를 산다. 즉 **방치 사망의 원인은 순전히 조작 부재**고, AI 가 사람을 편애하지
않는다는 뜻이다. 난이도가 오를수록 둘 다 짧아지는 것도 규칙대로다.

이 측정을 하다 §5.27 의 `shouldAttack` 누락이 나왔다. 원인을 캐는 계측이 규칙
누락을 찾아 준 셈이다.

### ⚠ 이식 누락 열 — 사람이 명령하는 퇴각

동맹이 맺어졌을 때의 **자동** 퇴각만 있었고, 사람이 물릴 방법이 없었다. 잘못 찍은
공격을 되돌릴 수 없으면 클릭 한 번이 곧 손실이 된다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 명령 → 실행 | 2초 | `RetreatExecution` 의 `cancelDelay = 20` |
| 사람을 치던 부대 | **25% 손실** | `malusForRetreat` |
| 중립 확장 | 손실 없음 | `retreat()` 를 인자 없이 부른다 |

명령 즉시 진격이 멈추고 2초 뒤에 물러난다. 즉시 물리면 되돌릴 수 없는 클릭 한
번으로 부대가 증발한다. 중립이 공짜인 이유는, 잘못 찍은 확장을 취소하는 데 병력을
버리게 하면 안 되기 때문이다.

⚠ **자리를 잘못 잡을 뻔했다.** 방사형 메뉴에 넣었다가 루트 구성 테스트가 깨졌고,
원본을 보니 퇴각은 메뉴가 아니라 **전투 패널(`AttacksDisplay`)의 ❌ 버튼**이었다.
진행 중인 공격 옆에 붙어 있어야 무엇을 물리는지가 분명하다.

⚠ **테스트가 병력 상한에 삼켜졌다.** 처음에 병력을 400,000 으로 두었는데 그 판의
상한이 123,200 이라, `_grow` 가 매 tick 큰 폭으로 깎아 **돌아온 병력이 그대로
사라졌다** — 반환을 아예 안 해도 통과했을 것이다. 상한 아래로 낮추고, 성장분을
지우려고 "공격을 안 한 같은 판"을 대조군으로 두고 잰다.

### §5.29 원본 소스를 손에 두고 작업하게 됐다

지금까지는 원본을 문서(이 파일)로만 참조했다. 남은 항목 셋(`DeleteUnitExecution` ·
`BoatRetreatExecution` · `EmbargoAllExecution`)은 이 문서에 **이름과 한 줄**밖에
없어서 값을 확인할 방법이 없었다. 그래서 원본을 얕게 클론했다:

```bash
git clone --depth 1 --filter=blob:none --no-checkout     https://github.com/openfrontio/OpenFrontIO.git of
cd of && git sparse-checkout set --no-cone "src/core/**" && git checkout
```

⚠ `--no-cone` 패턴은 `"/src/core"` 가 아니라 **`"src/core/**"`** 여야 한다. 앞의 형태로
쓰면 체크아웃이 조용히 성공하고 `src/` 가 없다 — 오류가 안 난다.

그리고 바로 **이 문서가 틀린 곳을 하나 찾았다.**

### ⚠ 이식 누락 열하나 — 건물 철거

한 번 지은 것을 영영 되돌릴 수 없었다. 방어초소를 잘못 놓아 도시 자리를 막았거나
(§5.21 에서 실제로 방어초소 41개를 짓고 도시 0개인 AI 를 봤다), 값이 상한에 걸린
건물이 자리만 차지하고 있어도 손쓸 방법이 없다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 명령 → 소멸 | **30초** | `Config.deletionMarkDuration()` = `30 * 10` |
| 다음 철거까지 | **30초** | `Config.deleteUnitCooldown()` = `30 * 10` |
| 골드 환불 | **없다** | `UnitImpl.delete()` 어디에도 없다 |
| 취소 | **없다** | 예약을 푸는 경로가 `setOwner()` 하나뿐이다 |
| 표시 기간 중 | **건물은 그대로 동작한다** | `_deletionAt` 만 세운다 |

⚠ **이 문서가 "쿨다운 10 tick" 이라고 적고 있었다. 틀렸다 — 300 tick 이다.**
30배다. 이름만 적어 두고 값을 확인하지 않은 항목이 어떻게 되는지 보여주는 사례다.
같은 이유로 **`lastDeleteUnitTick` 의 초기값이 −1** 인 것도 문서에 없었다 — 그래서
판 시작 후 30초는 철거를 못 한다.

⚠ **비용이 되돌아온다.** 철거하면 다음 같은 건물이 **다시 싸진다** — 비용이
`min(unitsOwned, unitsConstructed)` 이고(`Config.costWrapper`) 철거는 `unitsOwned`
만 줄이기 때문이다. 반직관적이라 "값은 절대 안 내려간다"고 지레짐작하고 `constructed`
쪽을 보게 고치기 쉬운데, 그러면 원본과 어긋난다. 골드가 안 돌아오므로 이득은 아니다.

자리는 **건설 메뉴 끝**에 뒀다. 원본은 유닛 아이콘을 직접 누르지만 우리 조작은
칸 단위라, 클릭한 칸 반경 7 안의 내 건물을 집는다 — 건물끼리 최소 15칸 떨어져
있으므로(`find_spot`) 반경 7 안에는 많아야 하나다.

### ⚠ 이식 누락 열둘 — 상륙 퇴각, 그리고 25% 가 사라져 있던 자리

배는 한 번 띄우면 끝이었다. 상륙은 병력의 상당 부분을 한 번에 태우는 행동이라
육상보다 되돌릴 수 없는 게 더 아프다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 명령 → 실행 | **지연 없음** | `BoatRetreatExecution` 에 `cancelDelay` 가 없다 |
| 퇴각 목적지 | 퇴각을 **시작한 위치** 기준, 한 번만 | `retreatDst ??= bestTransportShipSpawn(boat.tile())` |
| 내 땅에 닿으면 | **25% 손실** | `const malusForRetreat = 25` |
| 돌아갈 해안이 없으면 | **손실 없이** 전원 환원 | `retreatDst === false` 분기 |

⚠ **`BOAT_RETREAT_MALUS_PCT = 0.0` 이 박혀 있었다.** 상수는 이름까지 맞게 있었는데
값이 0 이고 아무도 안 읽었다 — 퇴각 기능 자체가 없었으니까. 그리고 이 25% 는
**퇴각 전용이 아니다**: 목적지가 그 사이 내 땅이 된 배도 같은 값을 뗀다. 우리는
그 자리에서 병력을 100% 돌려주고 있었다. 즉 **기능 하나가 없어서 규칙 하나가
같이 없었다.**

⚠ **변이 하나가 살아남았고, 테스트가 아니라 지도가 문제였다.** "퇴각 목적지를 매
tick 다시 고른다"는 변이가 통과했는데, 그건 테스트 지도에서 내 해안이 한 칸뿐이라
**다시 골라도 같은 답이 나왔기** 때문이다. 무동작 변이였다. 위아래에 육지를 둔
지도로 바꿔 항로 도중에 더 가까운 해안이 **생길 수 있게** 만들자 잡혔다.
*변이가 통과하면 테스트를 의심하기 전에 변이가 진짜 동작을 바꿨는지 본다* 를
또 확인한 셈이다.

### 전체 금수 — 봇을 빼는 것이 규칙이다

편의 기능으로 분류해 뒀는데, 실제로는 **필터가 규칙**이었다.

| 규칙 | 값 | 출처 |
|---|---|---|
| 봇 | **건너뛴다** | `if (p.type() === PlayerType.Bot) continue` |
| 이미 걸린 상대 | 다시 안 건다 | `if (!me.hasEmbargoAgainst(p))` |
| 쿨다운 | 10초 | `Config.embargoAllCooldown()` = `10 * 10` |
| 걸 상대가 없으면 | 아예 못 누른다 | `canEmbargoAll()` 의 두 번째 관문 |

봇을 빼는 이유가 우리 판에서 특히 크다 — 지도에 봇이 400개라, 봇까지 걸면 이건
"전체 금수"가 아니라 **무역 끄기 버튼**이 된다. 그리고 이미 걸린 상대를 다시 걸면
관계 −20 이 겹쳐 붙어 버튼 한 번이 관계를 −40 태운다.

자리는 **`E` 키**다. 방사형 메뉴는 상대 하나를 전제로 열려서 "모두에게"가 들어갈
자리가 없다(원본도 메뉴가 아니라 순위표 옆 버튼이다).

### §5.30 원본을 **실행해서** 대조하기 시작했다 — oracle 이 다시 돌아간다

§5.29 에서 소스를 옆에 뒀지만 여전히 *읽고* 있었다. 업그레이드를 붙이다 값이
의심스러워 `tools/oracle.mts` 와 같은 방식으로 **원본 `Config` 를 실제로 실행**해
봤고, 우리가 틀렸다는 것이 그 자리에서 나왔다.

되살리는 데 걸린 곳 세 군데(다음 세션이 다시 겪지 않게):

1. `node --experimental-strip-types` 로는 안 된다. 원본이 `enum` 을 쓴다 →
   `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. `--experimental-transform-types` 는
   enum 은 되지만 디렉터리 import 에서 막힌다. **`tsx` 를 쓴다**(원본 리포에
   `npm install`).
2. sparse-checkout 을 `"src/**"` 로만 두면 **루트의 `package.json` 이 안 나온다** →
   `npm install` 이 ENOENT. 패턴에 `"/*" "!/*/"` 를 같이 준다.
3. `resources/tribeNameThemes.json` 을 import 하는 파일이 체인에 있다.
   `"resources/*.json"` 만 추가하면 된다(지도 바이너리는 안 받아도 된다).

전체:

```bash
git clone --depth 1 --filter=blob:none --no-checkout     https://github.com/openfrontio/OpenFrontIO.git of
cd of
git sparse-checkout set --no-cone "/*" "!/*/" "src/**" "resources/*.json"
git checkout && npm install
./node_modules/.bin/tsx <스크립트>.mts
```

### ⚠ 이식 누락 열셋 — `unitsOwned` 는 개수가 아니라 **레벨 합**이다

건물 업그레이드를 UI 에 붙이려다 나왔다. 원본 실행 결과와 우리 값:

| | Lv1→2 | Lv2→3 | Lv3→4 | Lv4→5 |
|---|---|---|---|---|
| **원본(실행해서 받은 값)** | 250,000 | **500,000** | **1,000,000** | 1,000,000 |
| 우리 (고치기 전) | 250,000 | 250,000 | 250,000 | 250,000 |

`Config.costWrapper` 는 `min(unitsOwned(t), unitsConstructed(t))` 를 쓰는데,

```ts
unitsOwned(type) {
  for (const unit of this._units) if (unit.type() === type) {
    if (unit.isUnderConstruction()) total++;
    else                            total += unit.level();   // ← 레벨 합
  }
}
```

우리는 이걸 **개수**로 세고 있었다. 그래서 도시 하나를 250,000 에 무한히 올려
병력 상한을 사실상 공짜로 늘릴 수 있었다. `unitCount()`(기차 생성률이 읽는
`unitCount(Factory)`)도 같은 레벨 합이라 거기도 같이 어긋나 있었다.

⚠ **테스트가 틀린 값을 못 박고 있었다.** `test_upgrade_raises_level_and_next_price`
에 이렇게 적혀 있었다:

> "도시 1채를 계속 올리면 값이 그대로다 — min(보유1, 완공N) 이 1 에 묶인다.
> 직관과 다르지만 원본이 그렇다"

**틀렸다.** 반직관적인 결과를 만나면 "원본이 그렇다"고 적기 전에 원본을 돌려 봐야
한다. 이 주석은 자신 있게 쓰여 있어서 오히려 재검토를 막았다.

### ⚠ 이식 누락 열넷 — 건설 버튼이 곧 업그레이드 버튼이다

원본에는 "업그레이드"라는 별도 항목이 **없다.** 건설 메뉴의 같은 항목이, 같은
종류가 `structureMinDist`(15) 안에 이미 있으면 업그레이드가 된다:

```ts
// BuildMenu.sendBuildOrUpgrade
if (buildableUnit.canUpgrade !== false) → SendUpgradeStructureIntentEvent
else if (buildableUnit.canBuild)        → BuildUnitIntentEvent
```

`canUpgrade` 가 **먼저**다. 우리는 그 자리에서 `find_spot` 이 실패했다고
"지을 자리가 없다 — 건물끼리 15칸 떨어져야 한다"로 회색 처리하고 있었다. 즉
**사람은 도시를 두 채째부터 늘릴 방법이 아예 없었다.** 엔진에 `upgrade()` 는
있었지만 부를 길이 없었으니, 규칙이 있는데 못 쓰는 상태였다.

메뉴 옆의 숫자도 개수가 아니라 **레벨 합**이다(원본 `count()` = `totalUnitLevels`).
Lv3 한 채와 Lv1 세 채가 병력 상한에 같은 값을 내므로, 그렇게 보여야 판단이 맞는다.

⚠ **변이 하나는 잡히지 않는 게 정상이다.** `unitsOwned` 의
`1 if under_construction else u.level` 분기는 건설 중인 유닛의 레벨이 반드시 1 이라
**관찰 가능한 차이가 없다.** 원본 표현을 그대로 두려고 남긴 것이고, `units.py` 에
그렇게 적어 뒀다 — 다음 세션이 여기를 파지 않도록.

### §5.31 봇의 건설 — 우리 발명품 두 개를 원본으로 갈아 끼웠다

§5.30 에서 사람이 업그레이드를 쓸 수 있게 만들고 나니 **AI 는 업그레이드를 아예
안 하는 상태**가 남았다. 원본 `NationStructureBehavior`(1,354줄)를 옮겼다.

지우고 온 것이 둘이다. 둘 다 **원본에 없는 우리 발명품**이었다:

| 지운 것 | 무엇이었나 | 원본은 |
|---|---|---|
| `BUILD_WEIGHT` | 종류를 가중 무작위로 골랐다 | **도시 수 대비 비율**로 목표치를 정한다 |
| `STRUCTURE_CAP_PER_TILES` | 영토 대비 개수 상한 | 상한이 없다 — 초소가 건설 순서에 없어 필요가 없다 |

옮긴 핵심 넷:

1. **도시가 기준이다.** 항구·공장 0.75 · SAM 0.15~0.3(난이도) · 사일로 0.2.
   전부 `floor(도시레벨합 × 비율)` 이고, 못 미칠 때만 짓는다. 넷을 다 채우면
   그때 도시를 짓는다 — 이 **내림**이 원본이 도시를 우선하는 방식이다.
   비율만 보고 `round` 로 옮기면 도시 1채에서 바로 항구가 선다.
2. **밀도가 1/1500 을 넘으면 새로 짓는 대신 올린다.** 못 올렸으면(전부 건설 중,
   돈 부족) **짓지도 않고 기다린다.** SAM 처럼 건설이 긴 것이 줄줄이 서지 않게 하는
   장치다. 단 그 종류가 0채면 첫 채는 짓는다(작은 섬 대비).
3. **체감 비용.** 저축 목표(MIRV+수소탄)에 못 미치는 동안은 이미 가진 수만큼
   다음 건물이 비싸 *보인다*. 실제 값은 안 바뀐다. 목표를 넘기면 배수가 사라진다 —
   이게 없으면 부자 나라가 건물을 영영 못 짓는다.
4. **초소는 건설 순서에 없다.** 오직 육상 공격을 받는 중에만, 전선 근처에 짓는다.
   easy 는 아예 안 짓고, medium 은 1기, hard 이상은 위협 비율 0.4 마다 1기.
   위협 문턱(0.35)을 넘은 상태에서는 초소를 못 지었어도 **다른 건물도 안 짓는다.**

#### ⚠ 이식 누락 열다섯 — `Attack` 에 `sourceTile` 이 없었다

초소 조건을 옮기다 나왔다. 원본은 `sourceTile() === null` 인 공격, 즉 **육상 공격만**
센다 — 초소는 국경을 넘어오는 것을 늦추는 물건이라 배로 뒤를 잡힌 상황에는
소용이 없기 때문이다. 우리 `Attack` 에는 그 필드가 아예 없어 상륙과 육상을 구분할
수 없었다. `Attack.source_tile` 을 추가하고 상륙이 만드는 공격에 배가 내린 칸을 넘긴다.

이번에도 **UI/기능을 만들다** 나온 것이 아니라 **원본 코드를 실제로 옮기다** 나왔다.
§7 의 표에 새 경로로 적어 둔다.

#### ⚠ 열어 놓고 보니 다음 문제가 드러났다 — AI 가 가난하다

**원본 크기에서는 건물이 거의 안 는다.**

원인을 추측하지 않고 갈라서 쟀다(`map4x` · 나라 72 · 봇 100 · 4,000 tick):

> 살아 있는 나라 **29곳 전부**가 `_maybe_spawn(CITY)` 에서 막히는데, 막는 것이
> 체감 비용이 아니라 **실제 비용**이었다. 보유 골드 19,368~163,812 대 실제 값
> 250,000. 체감 비용(500,000)이나 저축 목표(30,000,000)는 애초에 닿지도 않는다.

즉 **이 규모에서 AI 나라는 두 번째 건물을 지을 돈이 없다.** 체감 비용 배수도,
밀도 문턱도, 업그레이드 점수도 그 뒤에 있어서 판에 거의 나타나지 않는다.

이건 §5.31 의 변경이 만든 것이 아니다 — 옛 AI 도 같은 골드로 돌았고 값도 같았다.
**가려져 있던 것이 드러난 것**에 가깝다: 예전에는 초소(25만 상한)를 계속 지어
골드를 소진했으므로 "돈이 없다"가 "건물이 안 는다"로 보이지 않았다.

**다음 세션의 후보다.** 어디를 봐야 하는지: `trade_gold`(무역선) · `train_gold`(기차) ·
`Config.goldAdditionRate`. 원본을 **실행해서** 같은 영토·같은 건물 구성의 초당 수입을
받아 오고 우리 값과 대조하는 것이 순서다(§5.30 의 방법). 지금 이 문서에는 그 대조를
한 기록이 없다 — **즉 아직 확인 안 한 항목이다**(함정 6번).

SAM 보호 점수 테스트도 처음엔 31:29 가 나와 "점수가 안 먹는다"고 오해할 뻔했다.
원인은 원본의 `chance(2)`(절반은 2·3위를 고른다)라 **후보가 둘이면 무엇을 해도
50:50** 이라는 것이었다. 후보를 여섯으로 늘리고 **SAM 없는 대조군**을 함께 재도록
고쳤다 — 대조군이 없으면 점수 계산을 통째로 지워도 통과한다.

### §5.32 골드가 판에서 증발하고 있었다

§5.31 이 "AI 가 가난하다"를 드러냈다. 원인을 찾으러 원본 수입 경로를 하나씩
따라갔다: `goldAdditionRate`(tick 당 100/봇 50) 는 우리와 같고,
`goldMultiplierFor` 는 로비 설정·호스트 치트라 우리에게 해당 없다. 무역·기차도
공식이 맞다. 그런데 **네 번째 경로가 우리에게 아예 없었다.**

#### ⚠ 이식 누락 열여섯 — 정복하면 상대의 골드를 가져간다

`GameImpl.conquerPlayer` 는 건물뿐 아니라 **골드도 넘긴다.** 우리는 건물만
넘기고 있었다:

```ts
const gold = skipGoldTransfer ? 0n : conquered.gold();
const goldCaptured = skipGoldTransfer ? 0n : this._config.conquerGoldAmount(conquered);
conqueror.addGold(goldCaptured);
conquered.removeGold(gold);          // ← 받는 양과 잃는 양이 다르다
```

규칙 셋:

1. **정복자가 받는 양** — 봇·나라는 전액, **사람은 절반**(`conquerGoldAmount`).
2. **패자가 잃는 양은 언제나 전액.** 그래서 사람을 정복하면 나머지 절반은
   어디로도 가지 않고 **사라진다.** 이 비대칭이 원본이다 — 사람을 터는 것이
   나라를 터는 것보다 남는 게 적다.
3. **한 번도 공격을 보낸 적 없는 사람은 이전 자체를 건너뛴다.** 시작 골드를
   켠 판에서 가만히 있는 사람을 털어 가는 것을 막는 장치다. 봇·나라에는 안 걸린다.

원본은 이 조건을 통계(`stats().attacks[ATTACK_INDEX_SENT]`)에서 읽는데 우리는
통계 계층이 없어 `PlayerState.attacks_sent` 를 새로 뒀다. 쓰이는 곳은 여기 하나뿐이다.

⚠ **이벤트를 재사용하면 안 된다.** 처음에 `CONQUERED_PLAYER` 로 골드를 실어
보냈는데, 그쪽 `amount` 는 **정복당한 사람의 pid** 라서(`ui/eventlog.py` 가 그렇게
읽는다) 소식창에 엉뚱한 이름이 찍힌다. `GOLD_FROM_CONQUEST` 를 따로 만들었다.

도시 레벨 합이 76 → 95 로 올라 그 문턱을 넘는 나라가 생겼다.

**판 길이는 안 바뀌었다**(양쪽 tick 9,000 종료). 경제만 커진 것이다.

⚠ **한 판·한 seed 다.** 이 문서의 규칙대로면 방향은 40판, 채택 판단은 240판이다.
사일로 1기는 "0이 아니게 됐다"이지 "핵이 판을 좌우한다"가 아니다. SAM 은 여전히 0기다.

### §5.33 대량 업그레이드 — 한 번에 최대 50레벨

사람은 한 번에 1레벨씩만 올릴 수 있었다. 도시 값이 25만 → 50만 → 100만으로
뛰므로 후반에는 여러 레벨을 한 번에 사는 것이 실제 조작이다.

#### 값은 `cost × 수량` 이 아니다

원본이 주석으로 못 박아 뒀다: *"upgrade costs escalate per level, so a bulk
total is NOT cost × amount"*. 한 레벨 올릴 때마다 `unitsOwned`(레벨 합)가
같이 오르므로 다음 값이 더 비싸다. 원본은 `cost(mg, this, n)` 으로
"이미 n채 더 가진 것처럼" 값을 매기는데, 우리 `units.cost(utype, extra=n)` 의
`extra` 가 정확히 그 자리다 — `bulk_cost` 는 그 합이다.

도시 1채 보유 기준: 1레벨 250,000 · 2레벨 누적 750,000 · 3레벨 누적 1,750,000.
선형으로 매기면 3레벨이 750,000 이라 **2.3배 싸게 파는 셈**이 된다.

#### 결제는 미리 합산하지 않는다

`UpgradeStructureExecution` 은 `amount` 번 반복하며 **매 단계 다시 검사**한다:

```ts
for (let i = 0; i < this.amount; i++) {
  if (!this.player.canUpgradeUnit(this.structure)) break;
  this.player.upgradeUnit(this.structure);
}
```

즉 골드가 중간에 떨어지면 거기까지만 오르고 멈춘다. `bulkCost` 는 **미리 보여주기
위한 것**이지 결제 경로가 아니다. 그래서 `upgrade()` 가 bool 이 아니라 **실제로
오른 레벨 수**를 돌려주게 바꿨고, UI 는 "5레벨 중 4레벨만 올렸다"를 그대로 알린다 —
그걸 안 알려주면 사람은 골드가 왜 줄었는지 알 수 없다.

#### 네 칸은 늘 같은 자리 — 중복도 지우지 않는다

원본 `RadialMenuElements` 는 `[1, 5, 10, 지금 살 수 있는 최대]` 네 칸을 고정한다.
주석의 이유가 하나뿐이다 — *"fixed positions for muscle memory"*. 살 수 없는
칸도 숨기지 않고 회색으로 남긴다.

⚠ **최대가 5나 10과 겹쳐도 칸을 지우지 않는다.** 원본 코드에 중복 제거가 없다
(`const slots = [1, ...steps, maxAmount]`). 처음에 "같은 수가 두 번 뜨는 건
버그겠지" 하고 중복을 지웠는데, 그러면 칸이 셋으로 줄어 **자리가 밀린다** —
자리 고정이 이 배치의 유일한 목적이므로 그게 진짜 버그다. 원본대로 되돌렸다.

#### ⚠ 원본에 있는데 우리에 없는 것 — 핵도 한 번에 여러 발이다

같은 메뉴를 옮기다 나왔다. `isStackableNuke` 경로가 있고, 원자탄은 사일로에
장전된 수(`readyMissileCount()`)만큼 **한 번에 여러 발을 살 수 있다.**
단계도 다르다 — `NUKE_BULK_STEPS = [2, 5]`(구조물은 `[5, 10]`). 주석에 이유가
적혀 있다: *"x2 is the standard play against a single SAM"* — SAM 하나를
뚫으려면 두 발이 기본이라는 것이다.

**아직 안 옮겼다.** 이번 작업 범위(대량 업그레이드) 밖이라 §7 "남은 것"에
항목으로 넣는다. `readyMissileCount` 에 해당하는 개념(사일로 장전 수)이 우리에게
있는지부터 확인해야 한다 — **없을 가능성이 높고, 그러면 그것부터가 누락이다.**

테스트 485 → 493. 변이 9개 전부 잡힘.

### §5.34 발사관 — 사일로도 SAM 도 재장전이 없었다

§5.33 에서 "핵도 한 번에 여러 발을 산다"를 발견하고, 그 상한인
`readyMissileCount()` 가 우리에게 있는지 확인하러 갔다가 **규칙 누락 둘**이 나왔다.
문서에 "**없을 가능성이 높고, 그러면 그것부터가 누락이다**"라고 적어 둔 그대로였다.

#### ⚠ 이식 누락 열일곱 — 사일로 발사관

```ts
readyMissileCount(): number {
  return this.units(UnitType.MissileSilo).reduce((acc, silo) =>
    silo.isUnderConstruction() ? acc
    : acc + Math.max(0, silo.level() - silo.missileTimerQueue().length), 0);
}
```

**발사관 수 = 레벨이다.** Lv3 사일로는 관이 셋이고, 쏜 관만 재장전 큐에 들어가
`SiloCooldown()` = **90 tick**(9초) 뒤에 열린다. 관이 전부 차면 그 기체는
쿨다운이다(`isInCooldown` = `length === level`).

우리는 이게 통째로 없었다 — **사일로 한 기로 골드가 되는 한 무한 연사**였다.

#### ⚠ 이식 누락 열여덟 — SAM 도 같은 발사관을 쓴다, 이쪽이 더 무겁다

`SAMCooldown()` 도 90 이고 구조가 같다. 그런데 우리 `_sam_intercepts` 는
사거리 안이면 **무조건, 무한히, 100%** 요격했다. 즉 **SAM 한 기가 판의 모든 핵을
영원히 막고 있었다.**

§5.9 에 적어 둔 "실전에서 핵이 한 발도 안 나간다"를 그동안 **경제 탓으로만** 보고
있었는데(§5.32 에서 정복 골드로 사일로가 0→1기가 됐다), 절반은 이쪽이었다.
쏠 돈이 생겨도 SAM 하나가 다 받아냈을 것이다.

#### 원본이 사일로와 SAM 을 **다르게** 처리하는 자리

같은 상수(90)를 쓰지만 재장전 처리 횟수가 다르다:

| | 원본 | tick 당 열리는 관 |
|---|---|---|
| `MissileSiloExecution` | `if (cooldown <= 0) reloadMissile()` | **하나** |
| `SAMLauncherExecution` | `while (...) { ... reloadMissile() }` | **끝난 것 전부** |

Lv3 사일로가 세 발을 같은 tick 에 쐈으면 90 tick 뒤에 관이 **하나만** 열리고,
그다음 tick 에 또 하나 열린다. `while` 로 합치면 셋이 한꺼번에 열려 연사 간격이
사라진다 — **상수가 같다고 코드를 합치면 안 되는 자리다.** 그래서 `Unit` 에
`reload_front`(하나)와 `reload_ready`(전부)를 따로 뒀다.

#### 레벨을 올려도 새 관은 재장전부터 시작한다

`UnitImpl.increaseLevel` 이 사일로·SAM 이면 큐에 `push` 한다. 즉 업그레이드가
즉발 화력이 되지 않는다. 이게 없으면 **쿨다운에 걸릴 때마다 업그레이드를 눌러
한 발씩 더 쏘는** 조작이 생긴다. (`decreaseLevel` 은 `pop` 한다 — 우리는 아직
레벨 감소 경로가 없어 옮기지 않았다.)

#### AI 도 관을 먼저 본다

원본 `NationNukeBehavior` 는 사일로마다
`availableSlots = level - missileTimerQueue.length` 를 보고 0이면 건너뛴다.
우리 `ai/nation.py` 는 "사일로가 하나라도 있으면" 으로 들어가고 있었는데,
그러면 재장전 중일 때 `launch_nuke` 가 조용히 `None` 을 돌려주고 **그 봇의 판단
tick 이 통째로 날아간다**(전함도 안 짓는다). `st.ready_missiles(pid) > 0` 으로 바꿨다.

#### 실측 — **판이 하나도 안 바뀌었다. 그게 정상이다**

`map` · 나라 72 + 봇 400 · seed 1. 정복 골드까지만 넣은 판과 **완전히 동일**하다:
도시 87(레벨합 95) · 초소 56 · 항구 46 · 공장 3 · 사일로 1 · 합계 193 ·
tick 9,000 정복 종료. 한 채도 다르지 않다.

이유는 소식 통계에 있다 — **판 전체에서 핵이 0발 나갔다.** 사일로는 tick 8,000 에
한 기 생겼고 판은 9,000 에 끝났다. **발사가 0이면 발사관 규칙은 발동할 자리가 없다.**
같은 결과가 나오는 것이 맞고, 다르게 나왔다면 그게 버그다.

⚠ **즉 §5.9 의 "실전에서 핵이 한 발도 안 나간다"는 아직 그대로다.** §5.32 가 사일로를
0→1기로 만들었고 §5.34 가 규칙을 맞췄지만, **발사 자체가 아직 안 일어난다.**

#### 그래서 왜 안 쏘는가 — 갈라서 쟀다

추측하지 않고 관문 셋을 각각 계수했다(`map` · 나라 72 + 봇 400 · seed 1 · 완주):

| 관문 | 표본 |
|---|---|
| 관이 없다(재장전 중) | 0 |
| **골드 부족(원자탄 750,000)** | **3** |
| 적이 없다 | 0 |
| `shouldAttack` 이 막음 | 0 |
| 쏠 수 있었다 | **0** |

> 사일로 보유 나라: **판 전체에서 1곳**
> 그 나라의 **최고 골드: 444,400**
> 원자탄 값 750,000 을 넘긴 나라: **0 / 1**

**발사관도, 표적도, 사람 봐주기도 아니다. 골드다.** 사일로(1,000,000)를 짓고 나면
원자탄(750,000) 살 돈이 남지 않는다 — §5.32 에서 "나라들이 실제 비용조차 못 낸다"고
잰 것과 **같은 자리**다.

⚠ **즉 §5.9 의 "핵이 한 발도 안 나간다"의 남은 원인은 규칙이 아니라 경제다.**
지금까지 이 자리에서 규칙 누락을 셋 찾았는데(정복 골드 · 사일로 발사관 · SAM 발사관)
셋 다 메우고도 발사는 0이다. **다음은 수입 공식을 원본과 대조하는 것**이고, 그
대조를 한 기록이 이 문서에 아직 없다 — 함정 6번대로 **확인 안 한 항목**이다.
어디를 볼지: `tradeShipGold`(우리 `trade_gold`) · `trainGold`(`train_gold`) ·
`goldAdditionRate`(맞다고 확인함, tick 당 100/봇 50). 남은 둘을 §5.30 의 방법으로
**원본을 실행해서** 받아 와야 한다.

#### 테스트 493 → 510. 변이 11개 전부 잡힘

⚠ **또 재료가 문제였다(네 번째).** SAM 쿨다운 검사를 지우는 변이가 처음에
살아남았는데, 내 테스트가 핵을 **한 발만** 쏘고 있었다 — 한 발만 보면 검사가 있으나
없으나 결과가 같다. 두 번째 발이 통과하는지, 그리고 **재장전 뒤에는 다시 요격하는지**
(대조군) 둘 다 재도록 고치니 잡혔다.

### §5.35 수입 공식은 맞았다 — 틀린 것은 **무역선이 뜨는 횟수**였다

§5.34 가 "다음은 수입 공식 대조"를 남겼다. 여섯 경로 중 셋(`tradeShipGold` ·
`trainGold` · `tradeShipSpawnRate`)이 "대조 기록 없음"이었다.

**그런데 셋 다 이미 하네스에 들어 있었다.** `tools/oracle.mts` 가 `trade_gold` ·
`trade_spawn_rate` · `train_gold` · `train_spawn_rate` 를 전부 뽑고 있고
`verify_port.py` 가 대조하고 있었다. 돌려 보니 **185/185 일치**다.

```
trade_gold(50/100/300/600/1200) = 2541 · 5185 · 52500 · 104990 · 134999
trade_spawn_rate((0,0)/(3,0)/(0,400)/(5,100)) = 100 · 25 · 200 · 16
train_spawn_rate(0/1/10/50) = 150 · 165 · 300 · 900
train_gold = 10000 · 35000 · 25000 · 25000 · 25000 · 20000 · 10000 · 5000
```

⚠ **함정 6번을 반대 방향으로 밟았다.** "확인 안 한 항목"이라고 적어 둔 것이 실은
확인된 것이었다. 재개 지점 표를 쓸 때 하네스를 안 열어 봤다는 뜻이다 —
**문서에 "없다"를 적을 때도 확인이 필요하다.**

`goldAdditionRate` 도 다시 봤다: `PlayerExecution` 이 매 tick `100n`(봇 `50n`)을
그대로 더한다. 인구·노동자에 비례할 것 같은 이름인데 아니다. 우리 값과 같다.

#### 그래서 골드가 어디 있는지 **세어 봤다**

공식이 맞으면 남는 것은 유통량이다. `trade_gold` / `train_gold` 를 감싸 원본
크기(나라 72 + 봇 400, seed 1, world) 9,000 tick 을 완주시키며 경로별로 계수했다.

| 경로 | 횟수 | 골드 |
|---|---|---|
| 무역선 도착 | **29회** | 2,735,572 |
| 기차 도착 | 1,011회 | 14,930,000 |

**항구가 120곳인데 무역선 도착이 판 전체에서 29회다.** 기차의 1/35 이다.
평균 무역거리도 278 로 `tradeShipShortRangeDebuff`(300) 아래였다 — 시그모이드가
가장 세게 깎는 구간이다. 사일로는 0기, 핵은 0발.

#### ⚠ 이식 누락 열아홉 — 무역선 스폰이 항구마다가 아니라 판 전체 하나였다

원본은 `PortExecution` 이 **항구마다 하나씩** 붙어 있다. 우리는 `_advance_trade`
안에서 **판 전체가 매 tick 한 번** 굴리고 있었다. 여섯 가지가 한꺼번에 달랐다.

| | 원본 `PortExecution` | 우리 (전) |
|---|---|---|
| 굴리는 주체 | 항구마다 | 판 전체 하나 |
| 주기 | 10 tick (`checkOffset` 분산) | 매 tick |
| 굴림 횟수 | **레벨 횟수만큼** | 1번 |
| pity 카운터 | 항구마다 | 판 전체 하나 |
| 목적지 | 레벨·거리·동맹 **가중 목록** | 균등 무작위 2개 |
| 수로 검사 | 후보 단계에서 | 사후 경로 실패 |

```ts
shouldSpawnTradeShip(): boolean {
  const numTradeShips = this.mg.unitCount(UnitType.TradeShip);
  for (let i = 0; i < this.port!.level(); i++) {          // ← 레벨만큼
    const spawnRate = this.mg.config()
      .tradeShipSpawnRate(this.tradeShipSpawnRejections, numTradeShips);
    if (this.random.chance(spawnRate)) {
      this.tradeShipSpawnRejections = 0;                  // ← 그 항구만 리셋
      return true;
    }
    this.tradeShipSpawnRejections++;
  }
  return false;
}
```

**판 하나로 두면 세 가지가 동시에 죽는다.**

1. **항구를 지을 이유가 사라진다.** 항구가 2곳이든 120곳이든 유통량이 같다.
2. **레벨이 아무 일도 안 한다.** `unitsOwned` 가 레벨 합이었던 것과 같은 종류의
   누락이다 — 원본에서 레벨은 장식이 아니라 거의 항상 **곱셈 계수**다.
3. **pity 가 서로를 지운다.** 아무 항구나 한 번 성공하면 나머지 119곳의 빚이
   전부 0으로 돌아간다. 카운터가 쌓일 자리가 없으니 pity 자체가 사실상 없었다.

목적지 쪽도 통째로 없었다. `tradingPorts()` 는 **확률 목록**이다 — 같은 항구를
여러 번 밀어 넣어 가중치를 준다. 가중치 셋이 곱이 아니라 **합**으로 붙는다:
기본 레벨만큼 · 거리순 상위 1/3(`within(전체/3, 4, 전체)`) 이고 300 이상이면
레벨만큼 더 · 동맹이고 300 이상이면 레벨만큼 더. **300 미만이 보너스에서
빠지는 것이 핵심이다** — `trade_gold` 시그모이드가 그 구간을 크게 깎으므로
가까운 항구끼리 왕복하는 것이 이득이 되면 안 된다. 우리 평균거리가 278 이었던
것이 정확히 이 규칙이 없어서다.

`checkOffset = mg.ticks() % 10` 도 옮겼다. 항구가 생긴 tick 을 그대로 오프셋으로
쓴다 — 안 두면 전 항구가 같은 tick 에 굴어 유통량이 10 tick 주기로 뭉친다.
`decreaseLevel` 때와 달리 이건 우리에게 대응물이 있어서 그대로 옮겼다.

#### 실측 — 규칙 하나가 판을 바꿨다

같은 조건(world, 나라 72 + 봇 400, seed 1):

- *"로직과 배선을 따로 재야 한다"* — 순수 함수만 재면 엔진이 그 함수를 안 써도

- *"보호 장치는 막지 않았으면 무엇이 일어났을 것인가를 먼저 단언한다"* —
  10 tick 게이트는 "늘었다"가 아니라 **스폰 수가 tick 수의 1/10 을 넘을 수 없다**
  로 재야 잡힌다.

그리고 레벨 변이는 §5.34 에서 사일로에 당한 것과 **글자 그대로 같은 실수**다
(레벨을 전부 1로 두면 레벨 규칙을 지워도 결과가 같다). 문서에 적어 뒀는데도
같은 자리를 다시 밟았다 — 이제 Lv1 **대조군**을 함께 재는 형태로 고정했다.

### §5.36 무역선은 격침이 아니라 **나포**다 — 그리고 우리 전함은 움직이지 않고 있었다

§5.35 를 대조하다 표에 적어 둔 것을 바로 이어서 옮겼다.

#### ⚠ 이식 누락 스물 — 나포

우리 `_fire_shell` 은 무역선을 만나면 목록에서 **지웠다**. 격침이다.
원본은 포탄을 쏘지 않는다 — `huntDownTradeShip` 으로 **쫓아가서 잡는다.**

```ts
if (dist <= 5) {
  this.warship.owner().captureUnit(target);   // 소유자가 바뀐다
  this.warship.recordTradeCapture();
  ...
}
```

그리고 잡힌 배가 목적지에 닿으면 **나포한 쪽이 전액을 번다**:

```ts
if (this.wasCaptured) {
  this.tradeShip!.owner().addGold(gold, this._dstPort.tile());   // 한 명
} else {
  this.srcPort.owner().addGold(gold, ...);                        // 양쪽
  this._dstPort.owner().addGold(gold, ...);
}
```

**격침으로 두면 골드가 아무에게도 안 간다 — 증발한다.** 나포는 그 골드를
해적에게 옮기는 것이라 방향이 반대다. 원본 통계에 `piracyGold` 가 `tradeGold` ·
`trainGold` 와 나란히 별도 항목으로 있을 만큼 **독립된 수입 경로**다.

나포되면 배는 **해적의 가장 가까운 항구**로 뱃머리를 돌린다. 원래 목적지로
계속 가면 잡은 의미가 없다. 갈 수 있는 항구가 없으면 원본도 배를 지운다.

관문도 함께 옮겼다(`findBestTarget` 의 `includeTradeShips` 분기):

| 관문 | 왜 있나 |
|---|---|
| `hasReachablePort` | 끌고 갈 곳이 없으면 아예 안 노린다 |
| `isSafeFromPirates` | 해안선 물 칸을 밟으면 **20 tick** 은 못 건드린다 — 항구 앞에서 잡히지 않게 |
| 목적지가 나/내 동맹 | 어차피 내가 벌 배다 |
| `warshipPatrolRange`(100) | 사거리(130) 안이어도 순찰 구역 밖은 안 쫓는다 |

#### ⚠ 그런데 더 큰 것이 나왔다 — 우리 전함은 **아예 움직이지 않았다**

나포를 붙이고 테스트를 돌리니 하나도 안 잡혔다. 원인은 나포 규칙이 아니었다.
`Warship.patrol_origin` 이 필드로만 있고 **아무도 배를 옮기지 않고 있었다.**
우리 전함은 태어난 자리에 붙박여 사거리 안을 포격하는 포대였다.

격침에서는 이게 안 드러난다 — 사거리(130) 안이면 그 자리에서 쏘면 되니까.
**나포는 거리 5 안에 들어가야 성립하므로 그 순간 드러났다.** UI 를 만들면
규칙 버그가 나온다던 것과 같은 구조다: *새 규칙을 붙이면 옛 누락이 드러난다.*

`huntDownTradeShip` 의 추격을 그대로 옮겼다:

- **tick 당 2칸이다.** 원본이 루프를 두 번 돈다. 무역선도 1칸/tick 이라
  같은 속도면 영원히 못 따라잡는다 — 추격 자체가 성립하지 않는다.
- 근접에서는 경로 탐색이 아니라 **탐욕**으로 간다(`bestNeighborToward`).
  원본 주석: 축소 지도 경로가 대각으로 튀어 수렴이 안 된다.

⚠ **순찰 이동 자체는 아직 안 옮겼다.** 표적이 없을 때 전함이 순찰 구역을
돌아다니는 것, 그리고 `docked`/`retreating` 상태 기계가 통째로 없다. 지금은
무역선을 쫓을 때만 움직인다. "그 밖" 표에 넣었다.

#### ⚠ 재료 문제 — 테스트 지도에만 해안선이 없었다

`isSafeFromPirates` 테스트를 쓰다 알았다. `GameMap.from_rows`(테스트 픽스처)가
`SHORELINE_BIT` 를 **한 번도 안 세운다.** 실제 지도는 바이너리에 이미 들어 있어
멀쩡하다. 그래서 **해안선에 걸린 규칙은 테스트에서 영원히 발동하지 않는다.**

원본 `WaterManager` 의 정의를 그대로 옮겼다 — 이웃 중 육/수가 반대인 것이
있으면 해안선이고, **통행불가 이웃은 해안선을 만들지 않는다**(빈 공간이지
해안이 아니다).

⚠ 처음에 파이썬 루프로 썼더니 스위트가 **2.4초 → 8.1초**가 됐다. 테스트가
지도를 수백 번 만든다. numpy `roll` 로 바꿔 3.0초로 되돌렸다.

#### 테스트 522 → 532. 변이 12개 — 처음엔 5개가 살아남았다

| 살아남은 변이 | 왜 안 잡혔나 |
|---|---|
| 항구 없는 전함도 노린다 | 노렸다가 실패해 배가 **삭제**되는데 `captured_by is None` 만 봤다 |
| 항구 없어도 나포한다 | 엔진 경로로는 `hasReachablePort` 가 먼저 막아 **분기에 못 닿는다** |
| 해안선 갱신 안 함 | 테스트가 `last_safe_tick` 을 **직접 세팅**해 엔진 코드를 안 탔다 |
| 추격 속도 1칸 | tick 을 넉넉히 줘서 1칸이든 2칸이든 결국 따라잡았다 |
| 나포 사거리 0 | 탐욕 이동이 결국 **같은 칸**까지 가서 거리 0 으로도 잡혔다 |

⚠ **다섯 다 재료 문제다(열 번째~열네 번째).** 새로 배운 형태가 셋이다:

- **부작용을 안 보면 "안 했다"와 "했다가 실패했다"가 구분되지 않는다.**
  `captured_by is None` 은 둘 다 참이다. 배가 목록에 남아 있고 손도 안 탔는지를
  함께 봐야 한다.
- **상태를 테스트가 직접 세팅하면 그 상태를 만드는 코드는 검사 대상에서 빠진다.**
  `last_safe_tick` 을 손으로 넣으니 엔진의 갱신 한 줄이 통째로 안 재졌다.
  해안선 칸을 실제로 밟게 해서 엔진이 스스로 찍게 두니 잡혔다.
- **여유를 주면 속도·사거리 규칙이 안 재진다.** "결국 잡았다"는 1칸이어도,
  사거리가 0이어도 참이다. 거리를 세어 **딱 맞는 tick 수**만 주고, 전함을
  정확히 5칸 옆에 두고 **한 tick** 만 준다.

그리고 하나는 엔진 경로로 도달 자체가 안 됐다. `_capture_trade_ship` 을 직접
부르는 **계약 테스트**를 따로 뒀다 — 안전장치를 뜯어내도 스위트가 전부 통과하는
자리를 그대로 두지 않기 위해서다.

### §5.37 전함이 순찰하기 시작했다 — 그리고 좁은 지도가 다섯 개를 가리고 있었다

§5.36 에서 "순찰 이동은 절반만 옮겼다"고 적어 둔 것을 마저 옮겼다.

#### ⚠ 이식 누락 스물둘 — 순찰 이동

원본 `WarshipExecution.tick()` 은 **모든 분기의 끝에서 `patrol()` 을 부른다.**

```ts
if (target?.type() === UnitType.TransportShip) { this.shootTarget(); this.patrol(); return; }
if (target?.type() === UnitType.Warship)       { this.shootTarget(); this.patrol(); return; }
if (target?.type() === UnitType.TradeShip)     { this.huntDownTradeShip();          return; }
this.patrol();
```

**쏘면서도 순찰한다.** 무역선 추격만 예외인데, 그쪽은 이미 목표를 향해 움직이기
때문이다. `patrol()` 자체는 단순하다 — 목표 지점이 없으면 하나 뽑고, 그쪽으로
한 칸 간다. 닿으면 비우고 다음 tick 에 새로 뽑는다.

`randomTile()` 이 목표를 뽑는 규칙:

| 조건 | 값 |
|---|---|
| 중심 | **순찰 기점**(`patrolTile`) — 지금 위치가 아니다 |
| 범위 | 반경의 **절반**(`±warshipPatrolRange / 2`) |
| 지형 | 바다여야 하고, **해안선은 피한다**(`allowShoreline = false`) |
| 수로 | 전함이 있는 바다와 이어져 있어야 한다 |
| 실패 시 | 500번마다 반경 1.5배, 3번까지. 그래도 안 되면 해안선을 허용해 한 번 더 |

**중심이 기점인 것이 핵심이다.** 지금 위치를 중심으로 두면 무작위 보행이 되어
배가 표류하고, 순찰 구역이라는 개념이 사라진다. 그러면 §5.36 에서 옮긴
"순찰 반경 밖 무역선은 안 쫓는다"도 같이 무의미해진다.

#### ⚠ 재료 문제 — 테스트 지도가 순찰 반경보다 작았다

변이 8개 중 처음엔 **3개만 잡혔다.** 살아남은 다섯의 원인이 사실상 하나였다:
`state()` 헬퍼의 지도가 **62×30 인데 순찰 반경이 100 이다.** 반경의 절반(50)이
이미 지도 폭에 가까워, 반경을 두 배로 늘리든 중심을 옮기든 **결과가 같다.**

400×240 바다를 따로 만들어 다시 재니 둘이 바로 잡혔다.
**상수가 지도보다 크면 그 상수를 쓰는 규칙은 검사되지 않는다** — §5.10 의
"지도 규모 함정"이 이번엔 테스트 픽스처 쪽에서 나왔다.

나머지 셋은 각각 달랐다.

**1. 코드가 실제로 중복이었다.** 도착 처리를 두 벌 두고 있었다 —
`w.tile == w.patrol_target` 검사와, 이동 뒤 같은 검사. 한쪽을 지워도 다른 쪽이
가려 준다. `_step_toward` 가 목표 칸에서 `None` 을 돌려주므로 **같은 조건**이라
한 벌로 합쳤다. 변이가 안 잡히는 것이 테스트가 아니라 **코드가 중복이라는 신호**인
경우가 처음 나왔다.

**2. 벽에서 멀어 건너편이 후보에 안 들어왔다.** 수로 검사 테스트에서 배를 벽에서
100칸 떨어뜨려 뒀는데, 후보 범위가 ±50 이라 벽 너머가 애초에 안 뽑혔다.
벽 바로 옆으로 옮기니 잡혔다.

**3. 다른 두 검사가 지형 검사를 가려 주고 있었다.** 안쪽 육지는 **수로 검사**가
먼저 걷어내고(바다 이웃이 없어 성분이 비어 있다), 물가 육지는 **해안선 검사**가
걷어낸다. 그래서 지형 검사만 지워도 관찰 가능한 차이가 없다.
관찰 가능한 자리는 **해안선을 허용하는 폴백**뿐이다 — 거기서는 물가 육지가
성분 검사를 통과하므로 지형 검사가 유일한 관문이 된다. 칸이 전부 해안선인
2×2 못을 만들어(3×3 이면 가운데가 해안선이 아니다) 폴백을 강제로 태우고,
`_random_patrol_tile` 을 직접 40번 불러 계약을 걸었다.

교훈: **"관찰 가능한 차이가 없다"고 결론 내기 전에, 그 검사가 유일한 관문이 되는
상황을 만들 수 있는지 먼저 본다.** §5.30·§5.31 에서 그렇게 판정하고 넘긴 둘이
있는데, 이번 건은 만들 수 있었다.

### §5.38 다친 전함은 항구로 돌아간다 — 그리고 정박 자리는 레벨만큼이다

§5.37 이 "남은 것은 수리 후퇴와 정박"이라고 적어 둔 것을 마저 옮겼다.
이걸로 `WarshipExecution` 의 상태 기계가 다 들어왔다.

#### ⚠ 이식 누락 스물셋 — 수리 후퇴 · 정박

우리 전함은 다치면 **그 자리에서 계속 싸웠다.** 원본은 체력이 최대의 75% 아래로
떨어지면 가장 가까운 항구로 돌아가 정박한다.

| 규칙 | 값 | 왜 |
|---|---|---|
| `warshipRetreatHealthPercent` | 75 | 최대 체력의 비율이라 **베테랑 배도 같은 상대 체력**에서 나간다 |
| `warshipDockingRange` | 5 | 이 안에 들어오면 정박이다 |
| `warshipPortHealingBonusPerLevel` | 5 | 정박 회복 = **항구 레벨 × 5** |
| 정박 정원 | **항구 레벨** | 넘치면 옆에서 기다린다 |

**회복 풀을 정박한 배들이 나눠 갖는다.** 그래서 항구 레벨이 곧 수리 능력이고,
한 항구에 몰리면 각자 느려진다. 여기 소수가 생기므로 원본은
`activeHealingRemainder` 로 **나머지를 들고 간다** — 매 tick 잘라 버리면 회복량이
조용히 깎인다.

옮기면서 놓치면 안 되는 것 셋:

1. **후퇴 판정은 `healthBeforeHealing` 으로 한다.** 회복 뒤 값으로 보면 항구
   옆에서 tick 당 1씩 차오르는 배가 문턱을 오르내리며 후퇴를 껐다 켰다 한다.
   원본이 인자로 따로 넘기는 이유다.
2. **항구가 없으면 후퇴하지 않는다.** 갈 곳이 없는데 순찰을 멈추면 그냥 표적이 된다.
3. **후퇴 중에도 붙는 적은 쏜다**(`findRetreatAggroTarget`). 다만 그 목록에
   무역선은 없다 — 나포는 항구 반대 방향으로 끌려갈 수 있어 후퇴와 겹친다.

우리 쪽에 하나 더 붙였다: **클락에 표시된 쪽은 후퇴하지 않는다.** 그쪽은 애초에
수리가 안 되므로(§5.10 에서 옮긴 규칙) 돌아가 봐야 헛걸음이고, 순찰만 멈춘다.

#### ⚠ 변이 12개 중 처음엔 8개 — 살아남은 넷의 원인이 전부 달랐다

| 살아남은 변이 | 원인 |
|---|---|
| 회복 뒤 체력으로 판정 | **경계에서만 1 차이**다. 문턱 ±1 을 정확히 겨냥한 재료가 없었다 |
| 항구가 없어도 후퇴 | 코드가 중복 — None 검사를 두 갈래에 각각 뒀다 |
| 회복 나머지를 버린다 | 재료를 **두 번** 잘못 골랐다(아래) |
| 다 나아도 후퇴를 안 접는다 | 회복이 빨라(Lv8) **도착 전에** 다 나아서 정박 해제 경로를 안 탔다 |

**나머지 변이가 특히 고약했다.** 처음엔 Lv1 항구에 세 척을 태웠는데,
**정원이 곧 레벨**이라 한 척만 정박했다. 그래서 Lv4 로 올렸더니 이번엔
**정확히 나눠떨어졌다** — 풀이 `레벨 × 5` 이고 정원이 `레벨`이라, 가득 채우면
어떤 레벨이든 정확히 5씩이다. 소수가 생기려면 **정원보다 적게** 태워야 한다
(Lv4 에 3척 = 6.67). 그리고 한 tick 만 보면 들고 가든 버리든 6 이라
**여러 tick 을 합산**해야 드러난다(9 tick 이면 60 대 54).

교훈 둘:
- **상수 사이에 관계가 있으면 "가득 찬 경우"가 오히려 특이점이다.** 정원과 풀이
  같은 값에서 나오면 가득 채웠을 때 나머지가 사라진다.
- **누적으로만 드러나는 규칙은 한 tick 으로 못 잰다.** 나머지 처리·소수 분배는
  전부 이 부류다.

그리고 코드 중복이 또 나왔다(§5.37 에 이어 두 번째). None 검사를 두 갈래에 각각
두면 한쪽을 지워도 다른 쪽이 가려 준다. **한 곳으로 합치는 것이 답이지 테스트를
늘리는 것이 답이 아니다.**

### §5.39 자리 고르기 — §5.31 에서 보류한 값 함수 다섯을 옮겼다

"그 밖" 표에서 가장 큰 덩어리였다. §5.31 이 *"600줄, 철도 클러스터와 얽힌다"*
고 적어 두고 미뤄 둔 자리다.

#### ⚠ 이식 누락 스물넷 — 자리를 값으로 고르지 않고 있었다

우리 `_spawn_near` 는 **무작위 한 칸**을 골라 `find_spot` 으로 그 근처의 가장
가까운 빈자리를 썼다. 원본은 다르다:

```ts
const tiles = type === UnitType.Port
  ? this.randCoastalTileArray(25)
  : randTerritoryTileArray(this.random, this.game, this.player, 25);
const valueFunction = this.structureSpawnTileValue(type);
for (const t of tiles) {
  const v = valueFunction(t);
  if (v <= bestValue && bestTile !== null) continue;
  if (!this.player.canBuild(type, t)) continue;
  bestTile = t; bestValue = v;
}
```

**영토에서 25칸을 뽑아 값 함수로 점수를 매기고 가장 높은 칸에 짓는다.**
무작위 한 칸이면 고도도 국경 거리도 같은 종류와의 간격도 **아무 일도 안 한다** —
산 위 사일로도, 국경에 붙은 도시도, 항구 옆 항구도 그냥 나온다.

값 함수 다섯:

| 종류 | 항 |
|---|---|
| 항구 | 다른 항구와의 거리 **그것만**. 상한도 없다 |
| 사일로 | 고도 + min(국경거리, `borderSpacing`) + min(사일로거리, `structureSpacing`) |
| 도시 | 위 + **공장과의** 교차 간격 + 철도 연결성 × `structureSpacing` |
| 공장 | 위 + **도시와의** 교차 간격 + 철도 연결성. 같은 종류 상한만 `stationRange`(110) |
| SAM | 고도 + 국경 + SAM 간격 + **사거리 안 건물 하나당 `structureSpacing`** |

읽으면서 알게 된 것 넷:

1. **값은 곱이 아니라 합이다.** 그래서 SAM 의 "덮는 건물 수" 항이 지형·간격 항을
   압도한다 — 건물 하나가 `structureSpacing`(원자탄 반경 × 2) 만큼이다.
   SAM 은 자리보다 **무엇을 덮느냐**가 전부라는 뜻이다.
2. **상한이 걸린 항이 대부분이다.** "충분히 멀면 그만"이라는 뜻이고, 없으면
   영토 구석으로만 몰린다.
3. **항구만 고도도 국경도 안 본다.** 해안에만 서므로 자리가 이미 좁고, 무역선
   벌이가 거리에 붙어 있어(`tradeShipGold`) 퍼뜨리는 것 자체가 이득이다.
4. **공장이 도시보다 넓게 벌어진다**(110 대 `structureSpacing`). 역 사거리를
   넘겨야 노선이 생기기 때문이다.

`spacingConstants` 는 상수를 새로 두지 않고 **원자탄 바깥 반경**을 읽는다.
핵 반경이 지도 규모에 맞춰져 있으므로 여기도 자동으로 따라온다(§5.10 에서
한 번 데인 자리라 그대로 지켰다).

#### 철도 클러스터 — 유니온-파인드로 대신했다

원본 `StationManager` 의 `Cluster` 가 우리에겐 없다. 역 그래프의 연결 성분이
정확히 같은 것이라 유니온-파인드로 만들었다.

**연결성 점수가 클러스터마다 한 번만 세는 것이 핵심이다.** 같은 노선에 붙은 역
열 개가 열 배로 쳐지면 이미 이어진 자리에 계속 겹쳐 짓게 된다 — **새 클러스터를
잇는 자리**가 값져야 한다. 무게는 기차 벌이의 비율이다(동맹 1.0 > 남/팀 ~0.71 >
자기 ~0.29), 그래서 이웃과 이어지는 자리가 더 값지다. ⚠ 봇과 금수 상대는 뺀다 —
기차가 안 가는 곳이라 세면 안 된다.

연결성은 난이도로 걸린다(`shouldUseConnectivityScore`): easy 0% · medium 60% ·
hard 75% · impossible 100%.

#### 성능 — 재료를 tick 당 한 번만 모은다

국경 타일은 지도 전체를 훑는다. 후보 25칸마다 다시 모으면 판이 통째로 느려지므로
`Placement` 가 tick 당 한 번만 모으고, numpy 로 낸다(파이썬 루프는 처음부터
쓰지 않았다). 원본도 판단 한 번 안에서 `reachableStationsCache` 를 공유한다.

#### 테스트 552 → 574. 변이 15개 — 값 함수 11개는 한 번에 전부 잡혔다

살아남은 넷이 **전부 후보 뽑기 쪽**이었고, 원인이 넷 다 재료였다.

| 살아남은 변이 | 원인 |
|---|---|
| 지도 위쪽 가장자리를 국경으로 안 본다 | **왼쪽 열** 칸으로 쟀다 — 그 칸은 왼쪽 변 규칙이 이미 잡아 준다 |
| 값 함수 대신 아무 후보나 고른다 | 영토가 4×4 라 `STRUCTURE_MIN_DIST`(15)에 전부 걸려 **아무것도 못 지었고**, `if tile is not None` 로 감싼 탓에 **항상 참인 단언**이 됐다 |
| 후보를 25칸이 아니라 1칸만 본다 | `len(seen) <= 25` 로 단언했다 — 1칸도 참이다 |
| 항구도 영토 전체에서 후보를 뽑는다 | 영토에 해안이 없어 어느 쪽이든 `None` 이었다 |

⚠ **"항상 참인 단언"을 또 썼다**(§5.35 에 이어 두 번째). 이번엔 `if` 로 감싼
형태였다 — 조건이 거짓이면 단언이 통째로 안 돈다. 그리고 `<=` 로 쓴 상한 단언도
같은 부류다: **아래쪽이 안 막혀 있다.** 규칙이 "정확히 N"이면 `==` 로 쓴다.

교훈 하나 더: **네 방향·네 변처럼 대칭인 규칙은 각 변을 따로 재야 한다.**
한 변만 지우는 변이는 다른 변에서 잡히지 않는다.

### §5.40 골드를 어디에 쓰는지 셌더니 — **전함이 지출의 85%** 였다

§5.35~§5.39 로 수입이 6배가 됐는데도 §5.9 의 "핵이 안 나간다"가 안 풀렸다.
그래서 이번엔 **지출**을 종류별로 셌다. 원본 크기(나라 72 + 봇 400, seed 1)
9,000 tick 완주.

#### 수입 — 무역선 수정이 실제로 판을 바꿨다

| 경로 | 골드 | 횟수 |
|---|---|---|
| 무역선 | **600,051,158** | 4,950회 |
| 기차 | 16,610,000 | 1,151회 |

§5.35 이전 29회 → §5.35 직후 453회 → 나포·추격·순찰까지 넣은 뒤 **4,950회**다.
골드 최고도 242,548 → **17,777,973**. **사일로가 처음으로 섰다 — 0기 → 9기.**

#### 지출 — 여기서 다음 누락이 나왔다

| 항목 | 골드 | 횟수 | 비중 |
|---|---|---|---|
| **전함** | **535,000,000** | **2,140척** | **85%** |
| 업그레이드 | 33,500,000 | 35 | 5% |
| 항구 | 13,375,000 | 105 | 2% |
| 도시 | 13,250,000 | 106 | 2% |
| SAM | 10,500,000 | 7 | |
| 사일로 | 9,000,000 | 9 | |
| 공장 | 7,625,000 | 46 | |
| 초소 | 4,150,000 | 62 | |

생존 28명에 전함 2,140척. **1인당 76척**이다.

#### ⚠ 이식 누락 스물다섯 — 전함은 상비군이 아니라 대응 수단이다

우리 코드는 이랬다:

```python
if p.gold >= p.units.cost(UnitType.WARSHIP) and p.units.of(UnitType.PORT):
    ...  # 짓는다
```

**골드가 되면 무조건.** 원본은 두 겹으로 막는다:

```ts
if (!this.random.chance(50)) return false;          // ① 판단마다 50%
if (ports.length > 0 && ships.length === 0 && ...)  // ② 한 척도 없을 때만
```

`ships.length === 0` 이 핵심이다. **첫 한 척 뒤로는 새로 짓지 않는다.**
그 뒤 전함이 느는 길은 보복뿐이고, 그것도 상한이 있다:

```ts
if (this.player.units(UnitType.Warship).length >= 10) {
  this.maybeMoveWarship(tile);   // 짓는 대신 있던 배를 그리로 보낸다
  return;
}
```

보복 확률도 난이도를 탄다: easy 0% · medium 15% · hard 50% · impossible 80%.
**easy 는 아예 보복하지 않는다.**

그래서 원본의 해군은 작다. 전함은 바다를 채우는 상비군이 아니라 **당했을 때
내보내는 대응 수단**이고, 10척이 그 천장이다. 우리는 그 두 겹이 다 없어서
골드의 85% 를 바다에 부어 놓고 아무도 핵을 못 샀다.

함께 옮긴 것 둘:

- **스폰 자리는 항구 반경 250 안 아무 바다다**(`warshipSpawnTile`). 항구 **옆**이
  아니다. 배가 처음부터 흩어져 뜨고 그 자리가 곧 순찰 기점이 되므로(§5.37),
  항구 옆에 몰면 순찰 구역이 겹친다.
- **`maybeMoveWarship` 은 이미 이동 중인 배를 안 부른다**(기점에서 130 넘게
  떨어진 배). 부르면 가던 길을 버리고 되돌아와 아무 데도 못 간다.

보복 방아쇠로는 **무역선 나포**를 배선했다(§5.36 에서 나포를 만들어 뒀다).
원본은 배가 목록에서 사라졌는지가 아니라 **주인이 바뀌었는지**를 본다 —
도착·격침과 나포를 구분해야 하기 때문이다. 도착에 보복하면 안 된다.

#### 수송선 격침 보복도 이어서 옮겼다

방아쇠가 하나 더 있다 — **내 수송선이 격침당하면** 보복한다. 관계는 더 크게
깎인다(**−15** 대 무역선 −7.5). 병력을 실은 배라서다.

옮기면서 걸린 것은 **배가 목록에서 빠지는 이유가 셋**이라는 점이다:
도착 · 퇴각 완료 · 격침. 빠졌다는 것만으로는 구별되지 않는데 **도착에
보복하면 안 된다.** 원본은 유닛에 `wasDestroyedByEnemy`/`destroyer` 를 남기고
봇이 참조를 들고 있다가 나중에 본다. 같은 구조로 `TransportShip.sunk_by` 를
뒀다 — 핵에 날아간 배도 여기 기록한다(원본도 `delete(true, destroyer)` 로
같은 자리에 남긴다).

⚠ 아직 안 옮긴 것: 들어오는 상륙선에 대한 선제 대응
(`trackIncomingTransportsAndRetaliate`), 그리고 `counterWarshipInfestation`
(부자 나라가 바다를 독점한 상대를 견제하는 것). "그 밖" 표에 넣었다.

#### 테스트 574 → 592. 변이 18개 — 살아남은 여섯

| 살아남은 변이 | 원인 |
|---|---|
| 전함을 육지에도 띄운다 | `build_warship` 이 육지를 **다시 거른다** — 육지를 돌려줘도 짓기에 실패할 뿐이고 다음 tick 에 또 시도해 결국 짓는다 |
| 도착한 무역선에도 보복한다 | 목록에서 **빠진** 배로 쟀다. 빠진 배는 추적에서 지워져 보복 판단에 닿지도 않는다 |
| 이미 이동 중인 배도 다시 부른다 | 그 상황을 만드는 테스트가 아예 없었다 |
| 수송선 격침도 무역선과 같은 감소를 준다 | `relations.of()` 로 쟀다 — **구간(enum)** 이라 −15 든 −7.5 든 한 칸 내려가면 같다 |
| 도착한 배도 격침으로 표시한다 | 봇만 재고 **엔진 배선을 안 쟀다** |
| 핵에 날아간 배는 누가 쐈는지 안 남긴다 | 같은 이유 |

첫째는 §5.36·§5.37 에서 두 번 겪은 것과 같은 형태다 — **뒤에 있는 검사가
앞의 검사를 가려 준다.** 엔진 경로로는 못 잡고, 함수를 직접 부르는 **계약
테스트**로만 잡힌다. 게다가 재료도 필요했다: 육지가 후보에 실제로 많이 섞이는
지도라야 한다(바다뿐인 지도에서는 육지를 고를 일이 없다).

둘째가 새 형태다. **"안 하는지"를 재려면 그 판단에 실제로 닿아야 한다.**
사라진 배는 판단 전에 걸러지므로, 살아 있고 아직 내 것인 배를 계속 두고
보복이 안 나가는지를 봐야 "나포당했을 때만"이 재진다.

### §5.41 초소 자리 — 국경에 딱 붙던 것을 띠 안으로 옮겼다

§5.31 이 "간략화했다"고 적어 둔 `sampleTilesNearFront` 다. 전에는 전선 타일을
그대로 `find_spot` 에 넘겨 **가장 가까운 빈자리**를 썼다. 그러면 초소가 국경에
딱 붙어 서고, 여러 기를 지어도 같은 지점에 몰린다.

원본은 세 겹이다:

1. **퍼뜨리기** — 이미 초소가 있으면, 그 초소에서 `borderSpacing × 1.5` 밖인
   전선 타일만 기준점으로 쓴다. 하나도 안 남으면 전선 전체를 쓴다.
2. **국경 깊이 띠** — 기준점 주변에서 뽑은 칸이 국경에서
   `borderSpacing × 0.75 ~ 1.5` 안이어야 한다. 너무 앞이면 첫 공격에 넘어가고,
   너무 뒤면 전선을 못 덮는다.
3. **폴백** — 띠를 만족하는 칸이 하나도 없으면 깊이 조건을 풀고 다시 뽑는다.
   이게 없으면 **영토가 얇은 나라는 초소를 한 기도 못 짓는다.**

#### ⚠ 변이 하나는 도달할 수 없는 분기였다

띠의 **위쪽** 경계(`d > hi`)를 지우는 변이가 살아남았다. 테스트를 늘려도 안
잡히는데, 이유가 코드에 있다: 기준점이 국경 타일이고 **탐색 반경이 `hi` 와
같은 값**(`borderSpacing × 1.5`)이라 뽑힌 칸의 국경 거리가 `hi` 를 넘을 수가
없다. **원본도 같다.** 소스에 그렇게 적어 뒀으니 파지 말 것.

지금까지 "관찰 가능한 차이가 없다"로 판정한 것이 넷이 됐다(§5.30 · §5.31 ·
여기). §5.37 에서 배운 대로 **그 검사가 유일한 관문이 되는 상황을 만들 수
있는지 먼저 봤고**, 이번엔 만들 수 없었다 — 두 상수가 같은 값에서 나오기 때문이다.

#### ⚠ 그리고 내가 쓴 테스트 하나가 쓰레기였다

"몰리지 않았다"를 `top_spread <= top_plain` 으로 쟀는데 그건 **항상 참**이었고,
쓰지도 않는 헬퍼가 두 개 붙어 있었다. 뽑힌 칸이 기존 초소에서 **얼마나
떨어졌는지를 직접 재고** 초소가 없는 경우를 대조군으로 두는 형태로 다시 썼다.
`<=` 로 쓴 단언은 §5.39 에 이어 두 번째다 — **아래쪽이 안 막힌다.**

테스트 592 → 597. 변이 7개 중 6개 잡힘(나머지 하나는 위의 도달 불가 분기).

### §5.42 바다 독점 견제 — 부자만 나선다

`NationWarshipBehavior` 의 마지막 큰 조각이다. 한 나라가 전함으로 바다를 덮으면
남의 무역선·수송선이 통째로 막히는데(원본 주석이 *"warship infestation"* 이라
부른다), 그걸 푸는 장치다. **적 전함 옆에 내 전함을 띄운다.**

관문이 다섯이고 다 있어야 한다:

| 관문 | 왜 |
|---|---|
| hard 이상 | 원본 주석: *"Only the smart nations can do this"* |
| 판 전체 전함 > 10 | (아래 참조 — 성능용 이른 탈출이다) |
| 내 전함 < 10 | 견제한다고 내가 독점하면 안 된다 |
| 항구가 있다 · 골드가 된다 | |
| **내가 부자 상위 3** | 원본 주석: *"We don't want poor nations to use their precious gold on this"* |

마지막이 핵심이다. 이게 없으면 가난한 나라가 마지막 골드를 여기 쓰고 아무것도
못 짓는다 — §5.40 에서 잡은 것과 같은 종류의 낭비다.

⚠ **부자 판정은 사람을 세지 않는다**(`p.type() === PlayerType.Human` 을 뺀다).
사람이 부자일 때 봇들의 순위가 밀려 견제가 통째로 멈추면 안 되기 때문이다.

팀 모드 경로(`findTeamGameWarshipTarget`)는 안 옮겼다 — 우리는 FFA 만이다.

#### ⚠ 이른 탈출 하나가 또 도달 불가였다

"판 전체 전함 > 10" 을 지우는 변이가 살아남는다. 아래에서 **적 하나가 10척을
넘어야** 표적이 되므로, 판 전체가 10 이하면 애초에 표적이 나올 수 없다.
**원본이 그 줄을 둔 이유는 성능**이다 — 붐비지 않는 판에서 매 tick 전 함대를
세지 않으려는 것. 소스에 적어 뒀다. 이걸로 "관찰 가능한 차이 없음"이 다섯이 됐다.

#### ⚠ 배선을 또 안 쟀다

변이 8개 중 처음엔 5개만 잡혔는데, 그중 하나가 **`tick()` 에서 호출 자체를
지우는 것**이었다. 내 테스트가 전부 `_counter_infestation` 을 직접 부르고 있었다.
**로직과 배선을 따로 재야 한다** — §5.35 · §5.40 에 이어 세 번째다.
이제 `bot.tick()` 을 돌리는 테스트를 하나 뒀다.

테스트 597 → 606. 변이 8개 중 7개 잡힘.

### §5.43 들어오는 상륙선을 미리 친다 — `NationWarshipBehavior` 를 다 옮겼다

보복(§5.40 · §5.42)이 당한 **뒤**라면 이쪽은 당하기 **전**이다. 내 땅을 노리는
상륙선을 보면 목표 근처 바다에 전함을 미리 띄운다.

관문 셋이 이 기능을 쓸모 있게 만든다:

| 관문 | 값 | 왜 |
|---|---|---|
| 목표까지 남은 거리 | **20 이상** | 코앞이면 배를 띄워도 상륙이 먼저 끝난다 |
| 목표 근처 내 전함 | **90 안에 없어야** | 이미 덮은 자리에 또 띄우면 낭비다 |
| 상대 | 동맹이 아니어야 | |

⚠ **덮였는지는 배의 위치뿐 아니라 그 배의 순찰 기점으로도 본다.** 배가 잠깐
멀리 나가 있어도 기점이 목표 근처면 곧 돌아오므로, 위치만 보면 같은 자리에
두 척이 겹친다.

그리고 두 겹의 낭비 방지가 있다:

- **한 척에 한 번만** 대응한다(`dealtWithTransportShip`). 없으면 확률이 빗나갈
  때마다 매 tick 다시 시도해 §5.40 의 낭비가 되돌아온다.
- **한 tick 에 한 척만** 처리한다(원본의 `break`). 여러 척이 동시에 오면
  함대가 통째로 나간다.

이걸로 `NationWarshipBehavior` 는 다 옮겼다.

#### ⚠ 변이 10개 중 처음엔 5개 — 넷이 "뒤의 검사가 앞의 검사를 가려 준다"

| 살아남은 변이 | 원인 |
|---|---|
| 순찰 기점은 덮은 것으로 안 친다 | 배 **자체**를 가까이 뒀다 — 위치 검사가 먼저 잡아 기점 검사가 안 재졌다 |
| 〃 (2차에도) | 배를 x 축으로 250 떼려다 **지도 폭(300)을 넘겨 줄바꿈**돼 오히려 51칸 거리가 됐다 |
| 한 척에 여러 번 대응한다 | 띄운 배가 목표를 덮어 **커버 검사가 두 번째 시도를 대신 막았다** |
| 한 tick 에 여러 척 | 여러 척이 동시에 오는 재료가 없었다 |
| 퇴각 중인 배 | 그 상황을 만드는 테스트가 없었다 |
| 내 배에도 대응한다 | **도달 불가** — `is_friendly(pid, pid)` 가 항상 참이라 뒤의 동맹 검사에 이미 포함된다 |

둘째가 특히 고약했다. "전함이 한 척뿐"이라는 결과는 **규칙이 있든 없든 참**이다 —
막은 것이 `dealt` 표시가 아니라 커버 검사였기 때문이다. **결과가 아니라 판단이
몇 번 불렸는지를 세야** 구별된다. `_retaliate` 를 세는 스텁으로 바꿔 잡았다.

⚠ **좌표를 지도 밖으로 밀면 조용히 줄바꿈된다.** `ref(x, y)` 는 `y * width + x`
라서 `x` 가 폭을 넘으면 다음 줄로 넘어간다 — "멀리 둔" 배가 오히려 가까워진다.
거리를 벌릴 때는 **폭이 아니라 높이 쪽으로** 벌리거나 폭 안에 있는지 먼저 확인한다.
§5.37 의 "상수가 지도보다 크면 그 규칙은 검사되지 않는다"의 사촌이다.

교훈: **"부작용을 안 보면 구별되지 않는다"의 반대편도 있다** — 부작용이 *너무
잘* 보이면 그 부작용을 만든 것이 어느 규칙인지 알 수 없다. 그럴 땐 부작용을
끊고(스텁) **호출 자체를 센다.**

마지막 하나("내 배에도 대응한다")는 테스트를 늘려도 안 잡힌다. 원본이 그 검사를
둔 이유는 성능이다 — 내 배마다 거리·소유 검사를 도는 것을 아끼는 것. 소스에
적어 뒀다. "관찰 가능한 차이 없음"이 이걸로 **여섯**이 됐다.

테스트 606 → 618. 변이 10개 중 9개 잡힘.

### §5.44 핵 AI — 열 줄짜리 축소판을 원본으로 갈아 끼웠다. **§5.9 가 풀렸다**

`NationNukeBehavior` 는 원본 AI 중 가장 큰 파일이다(1,104줄). 우리 것은
`nation.py` 안의 **열 줄**이었다:

```python
biggest = max(foes, key=lambda q: st.tiles(q.pid))     # 영토가 가장 큰 적
tiles = st.gmap.owned_refs(biggest.pid)
st.launch_nuke(self.pid, utype, int(self.rng.choice(tiles.tolist())))   # 아무 칸에나
```

#### ⚠ 이식 누락 스물여섯 — 표적도 자리도 안 고르고 있었다

원본은 세 단계다.

**1. 표적 나라**(`findBestNukeTarget`) — 순서가 곧 우선순위다:
들어오는 공격(원본 주석 *"Most important!"*) → 동맹이 지목한 표적 → 가장
미워하는 상대 → FFA 왕관. 두 가지가 특히 중요하다:

- **부족(봇)은 절대 안 친다**(*"Don't nuke tribes"*). 봇은 400마리라 핵을 여기
  쓰면 나라끼리의 판이 아예 안 돈다. 우리는 봇도 쳤다.
- **훨씬 약한 상대는 건너뛴다**(*"we don't need nukes to deal with them"*).
  병력 상한이 내 절반 아래면 핵을 아낀다.

FFA 왕관 문턱은 난이도를 탄다(easy 40% · medium 30% · hard 20% · impossible
10%). ⚠ **점유율의 분모가 "낙진이 없는 땅"이다.** 낙진 땅을 세면 판이 망가질수록
점유율이 낮게 나와 아무도 왕관을 안 친다.

**2. 종류**(체감 비용) — 쏠수록 비싸 **보이게** 한다(MIRV 저축 흉내):
원자탄 **50%**, 수폭 **25%** 씩 오른다. 원자탄이 더 가파른 것이 규칙이다 —
후반에 원자탄을 덜 매력적으로 만든다. 그리고 **수폭 나라**(1/3 확률)는 심한
공격을 받는 중이 아니면 원자탄을 아예 안 쓴다. 이게 AI 마다 성격을 갈라 놓는다.

**3. 자리**(`nukeTileScore`) — 후보는 무작위 10칸 **+ 상대 건물 타일 전부**다.
건물 칸을 빼면 알짜를 영영 못 맞힌다(넓은 영토에서 무작위로 건물 위를 찍을
확률은 거의 0이다). 값은 반경 안 건물의 합이고 사일로가 가장 값지다:

| 사일로 | 도시 | 항구·공장 | 초소 |
|---|---|---|---|
| 50,000×레벨 | 25,000×레벨 | 15,000×레벨 | 5,000×레벨 |

여기서 사일로까지의 거리를 빼되(×30) **건물 값의 20% 는 남긴다** — 안 남기면
멀리 있는 알짜가 가까운 빈 들판보다 못해진다. 그리고 **최근에 때린 자리**
(600 tick 안, 안쪽 반경)는 1,000,000 을 깎아 사실상 금지한다.

⚠ 그리고 **반경 안이 전부 표적의 땅이어야 쏜다**(`isValidNukeTile`).
easy·medium 은 예외가 없고(*"nuke away from the border"*), hard 이상만 빈 땅을
허용한다(작은 섬을 치기 위해). **축소판은 이게 없어서 내 땅·동맹 땅을 같이
날렸다.**

팀 모드 경로와 impossible 전용 경로 셋(`findHighDensityTarget` ·
`isTrajectoryInterceptableBySam` · `maybeDestroyEnemySam`)은 안 옮겼다.
"그 밖" 표에 적었다.

**골드가 실제로 핵으로 흘러간다.** §5.32 부터 §5.44 까지 이어 온 사슬 —
정복 골드 → 발사관 → 항구별 스폰 → 나포 → 전함 상한 → 핵 AI — 의 끝이다.

#### 변이 17개 중 처음엔 15개

살아남은 둘이 **같은 이유**였다: 시험대의 영토가 넓어 **가운데 건물이 어차피
최고점**이라, 반경 검사를 지우든 건물 후보를 빼든 같은 칸이 나왔다.

- 반경 검사 → 영토를 **반경보다 좁게** 만들어 깨끗한 자리가 하나도 없게 했다.
  그러면 검사가 유일한 관문이 되어 "안 쏜다"가 관찰된다.
- 건물 후보 → 영토를 넓게 두고 건물을 **한 채만** 둬서, 뽑힌 칸이 그 건물
  자리인지를 봤다(무작위 10칸이 그 한 칸을 찍을 확률은 거의 0이다).

⚠ 재료로 또 데였다. 수폭 반경이 **100** 이라 300×200 지도로는 반경 검사용
영토(반경의 3배)가 지도를 벗어난다. 600×400 으로 키웠다 — §5.37 의 "상수가
지도보다 크면 그 규칙은 검사되지 않는다"가 이번엔 **지도 밖으로 넘치는** 형태로
나왔다.

### §5.45 성능 — 재 보니 추측 셋 중 **하나만 맞았다**

§5.35~§5.44 로 규칙이 맞아지면서 판당 벽시계가 324초 → **1,827초**(30분)가 됐다.
30분짜리 판으로는 밸런스를 못 잰다 — 채택 판단에 240판이 필요한데(`cli/play.py`)
그러면 5일이다.

⚠ §5.8·§5.20 에서 성능을 **세 번 헛짚었다.** 전부 측정 조건을 안 본 탓이다.
그래서 이번엔 재개 지점에 의심 자리 셋을 적으면서 **"전부 추측이다"** 라고
못 박아 뒀고, 고치기 전에 `cProfile` 을 돌렸다. 결과:

| 자리 | 누적 | 비중 | 예측 |
|---|---|---|---|
| **`water_path`** | 120.1초 | **63%** | ✅ 맞았다 |
| **`_apply_embargo_relations`** | 34.0초 | **18%** | ❌ **생각도 못 했다** |
| `_advance_attacks` | 13.7초 | 7% | — |
| `trading_ports` | — | 상위 25 밖 | ❌ 틀렸다 |
| `_blast_is_clean` | — | 상위 25 밖 | ❌ 틀렸다 |

**셋 중 하나만 맞았고, 1등이 아닌 2등은 아예 후보에도 없었다.** 세 번 헛짚은
뒤에 또 두 개를 헛짚은 셈이다 — 재는 것 말고는 방법이 없다는 뜻이다.

#### 1. `water_path` — 상자가 사실상 지도 전체였다

```python
margin = manhattan(src, dst) * 2.5 + 8
```

거리에 **비례하는** 여유다. 무역 항로가 짧던 시절엔 상자가 작았지만, §5.35 로
항로가 길어지면서 400칸짜리 항로면 여유가 1,008칸이 된다 — 상자가 지도를 덮고
BFS 가 바다를 통째로 훑는다. **한 번에 0.3초**였다.

**A\* 로 바꿨다.** 휴리스틱은 맨해튼 거리다. 4방향 이동에서 실제 거리를 절대
넘지 않으므로(허용적) **경로 길이는 BFS 와 같이 최단**이다. 다만 같은 길이의
경로가 여럿일 때 어느 것을 고르는지는 달라질 수 있다 — 항로가 조금 달라 보여도
길이는 같다. 상자는 안전망으로 남겼다.

#### 2. `_apply_embargo_relations` — 생존자 **전 쌍**을 매 tick 돌고 있었다

```python
for pid in alive:
    for other in alive:            # 472 × 472 = 222,784 쌍
        on = self.diplomacy.embargoed(other, pid)
```

`embargoed` 가 1,500 tick 에 **9,878만 번** 불렸다. 금수는 실제로 몇 건 안 되므로
**걸린 것만 돌면 된다.** `embargoes` 가 "내가 막은 대상"이라 역방향이 없었는데,
루프 앞에서 한 번 뒤집어 만든다. 그러면 살아 있는 사람 수가 아니라 **금수 건수**에
비례한다.

⚠ 이건 §5.35 가 만든 문제가 아니다. **처음부터 O(N²) 이었고, 지도 규모가
472명으로 커지면서(§5.9 의 "지도 규모" 누락) 조용히 비싸진 것**이다. 판이 느려진
원인을 최근 변경에서만 찾았으면 영영 못 봤다.

#### 실측 — 같은 조건으로 다시 쟀다

world 원본크기(나라 72 + 봇 400, seed 1) 1,500 tick, cProfile 포함:

| | 전 | 후 |
|---|---|---|
| 전체 | 191초 | **74초** (2.6배) |
| `water_path` | 120.1초 (63%) | **35.7초** (48%) |
| └ 한 번당 | 0.302초 | **0.090초** (3.4배) |
| └ `neighbors` 호출 | 3,929만 | **1,019만** (3.9배 감소) |
| `_apply_embargo_relations` | 34.0초 (18%) | **상위 25에서 사라짐** |
| `_advance_attacks` | 13.7초 | 13.7초 (안 건드렸다) |

`water_path` 는 **여전히 1등**이다(48%). 다만 절대값이 1/3.4 이고, 호출 자체가
1,500 tick 에 399회뿐이라 이제 남은 것은 "한 번이 비싸다"가 아니라 "**긴 항로는
원래 비싸다**"에 가깝다. 더 줄이려면 항로를 캐시하는 방식(`_path_cache` 의 적중률)
을 봐야 하는데, 그건 다음에 잰다.

#### 판당 벽시계 — **1,827초 → 767초**

프로파일러 없이 같은 조건(원본 크기, seed 1, 9,000 tick)으로 다시 쟀다.
**30분이 12.8분이 됐다.** 프로파일에서 본 2.6배와 실제 판의 2.4배가 맞아떨어진다
— 즉 프로파일러 오버헤드가 결과를 왜곡하지 않았다.

⚠ 그런데 **같은 seed 인데 판이 완전히 달라졌다.**

| | 전 | 후 |
|---|---|---|
| 핵 발사 | 233발 | **3발** |
| 골드 최고 | 1,402,590 | **44,855,310** |
| 업그레이드 지출 | 54,000,000 | **264,000,000** |
| SAM | 1기 | 19기 |

**A\* 가 항로를 바꾼 결과다.** 길이는 같지만 지나가는 칸이 달라지므로, 무역선이
나포당하는 위치가 바뀌고 → 보복 전함이 다른 자리에 뜨고 → 관계·공격이 갈린다.
판은 이런 변화에 대해 카오스적이다.

⚠ **한 판으로는 규칙 버그인지 seed 노이즈인지 판단할 수 없다.** 그래서 seed 를
셋 돌리면서 `maybe_send` 의 관문 여덟(사일로 없음 / 관 없음 / 표적 없음 / 봇 /
`shouldAttack` / 골드 부족 / 깨끗한 자리 없음 / 쏠 수 있었다)을 각각 셌다.
§5.34 에서 쓴 방법 그대로다 — **왜 안 쏘는지를 추측하지 않는다.**

### §5.46 반경 검사는 "원 전체"가 아니라 **정사각형 두 개의 테두리**다

§5.45 에서 성능을 고치자 같은 seed 의 판이 완전히 달라졌다(핵 233발 → 3발).
A* 가 항로를 바꾼 연쇄로 보였지만 **한 판으로는 판단할 수 없어서**, seed 를 셋
돌리며 `maybe_send` 의 관문 여덟을 각각 셌다(§5.34 의 방법).

#### 세 판 모두 안 쐈다 — seed 노이즈가 아니었다

| seed | 발사 | 생존 | 골드 중앙 | 사일로 |
|---|---|---|---|---|
| 1 | **0발** | 18 | 4,152,230 | — |
| 2 | **4발** | 25 | 3,884,048 | — |
| 3 | **1발** | 24 | 4,702,867 | 21기 |

관문 계수(seed 3)가 원인을 바로 가리켰다:

| 관문 | 횟수 |
|---|---|
| 사일로 없음 | 3,201 |
| 표적 없음 | 528 |
| **깨끗한 자리 없음** | **278** |
| 골드 부족(체감) | 146 |
| **쏠 수 있었다** | **1** |

사일로가 21기 있고 골드도 넘치는데, 판단에 도달한 뒤에는
**`깨끗한 자리 없음`이 `쏠 수 있었다`를 278 대 1 로 압도**했다.

#### ⚠ 내가 §5.44 에서 옮길 때 틀렸다

원본은 이렇게 검사한다:

```ts
const boundingBox = boundingBoxTiles(this.game, tile, range)
  // Add radius / 2 in case there is a piece of unwanted territory inside
  // the outer radius that we miss.
  .concat(boundingBoxTiles(this.game, tile, Math.floor(range / 2)));
for (const t of boundingBox) {
  if (!this.isValidNukeTile(t, nukeTarget)) continue outer;
}
```

`boundingBoxTiles` 는 **정사각형의 테두리만** 돌려준다(위·아래 변 + 좌·우 변).
즉 원본이 보는 것은 **두 개의 사각 테두리 위 칸들**이고, 안쪽은 안 본다.

나는 이걸 "반경 안 전체"로 옮겼다. 훨씬 엄격해서 **도시 하나, 남의 칸 하나만
반경 안에 있어도 걸린다.** 실제로 거의 아무 데도 못 쏘게 됐다.

원본 주석이 힌트를 다 줬는데 못 읽었다 — 안쪽 상자를 두는 이유가
*"바깥 반경 안에 낀 남의 땅 조각을 놓치지 않으려는 것"* 이라는 말은,
**바깥 테두리만으로는 새는 것을 알고 있으면서도 그렇게 둔다**는 뜻이다.
완벽한 검사가 아니라 **값싼 표본**이고, 그래서 핵이 실제로 나간다.

교훈: **"안전하게 더 엄격하게"가 이식에서는 틀린 것이다.** 원본이 허술해
보이는 자리는 대개 성능이나 게임성 때문에 일부러 그런 것이고, 조이면 그
기능이 통째로 죽는다. §5.34 의 발사관(SAM 이 무한 요격)이 정반대 방향의
같은 실수였다 — 그때는 너무 느슨해서 기능이 죽었다.

#### ⚠ 그런데 고쳐도 안 나갔다 — 병목이 아니었다

| seed | 원 전체 | 두 테두리 |
|---|---|---|
| 1 | 0발 | 0발 |
| 2 | 4발 | 5발 |
| 3 | 1발 | **0발** |

관문 계수도 `깨끗한 자리 없음` 278 → **282** 로 사실상 그대로다. 수정은 원본
소스와 대조해 확인한 것이라 되돌리지 않지만, **이것이 원인이라고 말하면 틀린다.**

#### 진짜 원인 — **부자가 될수록 핵이 멈춘다**

`_pick_type` 은 원본대로 **수폭을 먼저** 고른다:

```ts
if (!disabled(Hydro) && gold >= hydroCost) nukeType = Hydrogen;
else if (... && gold >= atomCost)          nukeType = Atom;
else return;
```

⚠ **자리를 못 찾아도 원자탄으로 되돌아가지 않는다.** 원본도 그렇다 — 그 판단
tick 이 통째로 날아간다.

여기에 반경과 지도 규모가 겹친다:

| | 값 |
|---|---|
| 수폭 검사 상자 | 한 변 **201칸** |
| 원자탄 검사 상자 | 한 변 61칸 |
| `map4x` 육지 | 158,068칸 |
| 생존 24명 시 1인당 | 6,586칸 = 한 변 **81칸** |

**수폭 상자(201)가 1인당 영토(81)에 들어갈 수가 없다.** 그래서 부자가 되어
수폭을 고르기 시작하면 그 뒤로는 아무 데도 못 쏜다.

이것이 §5.44 의 "233발"과 지금 "0~5발"을 가른다. §5.44 판은 골드 최고가
**1,402,590** 이라 수폭(5,000,000)을 못 사서 **원자탄**(상자 61칸)을 골랐고,
그건 영토에 들어간다. §5.45 이후 판은 골드가 24~34M 이라 전부 수폭을 고른다.

즉 **§5.35~§5.44 로 경제를 고친 것이 핵을 멈춘 원인**이다. 규칙 하나가 틀린
것이 아니라 **규칙들이 맞아지면서 드러난 규모 문제**다.

#### ⚠ 우리는 1/4 해상도로 돌리고 있었다

| 크기 | 해상도 | 육지 | 생존 24명 시 한 변 |
|---|---|---|---|
| `map16x` | 500×250 | 37,575 | 40칸 |
| **`map4x`**(기본) | 1000×500 | 158,068 | 81칸 |
| `map` | 2000×1000 | **651,569** | 165칸 |

4.5절 표의 **원본 World 육지가 651,569** 다 — 즉 `map` 이 원본이고 우리 기본은
그 **1/4** 이다. §5.18 에서 `map16x` → `map4x` 로 올렸고 §5.20 이 *"`map` 은
시뮬레이션이 무겁다(3.4ms vs 14.2ms/tick)"* 며 기본을 `map4x` 로 뒀다.

핵 반경은 원본 절대값이므로, 지도가 1/4 이면 **반경이 상대적으로 2배**다.
`map` 에서도 1인당 165칸이라 수폭 상자 201칸에는 못 미치지만, **1등은 평균의
몇 배**를 가지므로 거기서는 설 자리가 생긴다.

**그래서 원본 해상도로 돌려 확인한다.** 이건 추측이고, 다음 절이 그 실측이다.

### §5.47 원본 해상도로 돌리니 핵이 나갔다 — **`map4x` 가 원인이었다**

§5.46 의 가설을 실측했다. **같은 seed, 같은 코드, 해상도만 다르다.**

| 관문 | `map4x`(1000×500) | `map`(2000×1000) |
|---|---|---|
| 호출 | 4,108 | 6,704 |
| 사일로 없음 | 3,147 | 5,363 |
| 표적 없음 | 614 | 671 |
| 깨끗한 자리 없음 | 240 | 402 |
| 골드 부족(체감) | 222 | 222 |
| **쏠 수 있었다** | **0** | **26** |
| **발사** | **0발** | **10발** |
| 생존 | 18 | **39** |
| 골드 최고 | 34,284,731 | **11,663,856** |
| 벽시계 | 368초 | 1,072초 |

**`쏠 수 있었다`가 0 → 26 이다.** 규칙은 맞았고 **지도가 작았다.**

부수적인 것이 오히려 더 말해 준다: **생존이 18 → 39명**이고 **골드 최고가 3배
낮다.** 작은 지도에서는 정복이 빨라 소수에게 땅과 돈이 몰리는데, 원본 크기에서는
그게 훨씬 완만하다. §4.5 가 *"작은 지도에 그대로 넣으면 다른 게임이 된다"* 고
적어 둔 것이 핵 말고도 여러 자리에서 사실이었던 셈이다.

#### 왜 그동안 안 드러났나

§5.44 까지는 **아무도 부자가 아니어서** 원자탄(검사 상자 61칸)만 골랐고, 그건
`map4x` 의 1인당 영토(81칸)에 들어간다. §5.35~§5.44 로 경제가 맞아지면서
골드가 24~34M 이 되자 전부 수폭(상자 201칸)을 고르게 됐고, 그건 **어떤 영토에도
안 들어간다.** 원본과 마찬가지로 자리를 못 찾아도 원자탄으로 안 내려간다.

⚠ **규칙이 맞아질수록 규모 왜곡이 드러난다.** §4.5 · §5.10 이 "지도 규모"를
두 번이나 경고했는데, 그때는 *핵 반경이 지도에서 차지하는 비중* 이라는 형태였다.
이번에는 **AI 가 어떤 핵을 고르는지**를 통해 나왔다 — 같은 왜곡의 세 번째 얼굴이다.

#### ⚠ 해상도 기본값을 다시 판단해야 한다

§5.20 이 기본을 `map4x` 로 둔 근거는 **`map` 이 14.2ms/tick** 이라는 측정이었다.
그건 **§5.45(A* · 금수 O(N²)) 이전 값**이다. 낡은 측정으로 결정을 유지하지
않는다 — 다시 쟀다.

#### 다시 잰 결과 — **기본을 `map` 으로 올렸다**

나라 72 + 봇 400, 초반 1,200 tick(가장 붐비는 구간):

| 해상도 | 육지 | tick당 | 10Hz 예산(100ms) |
|---|---|---|---|
| `map4x` | 158,068 | 21.6ms | 여유 |
| **`map`** | 651,569 | **73.6ms** | **들어간다** |

§5.20 의 옛 값(3.4 / 14.2ms)과 자릿수가 다른 이유는 **플레이어 수가 다르기
때문**이다 — 그때는 진행 중인 일반 판이었고 이번은 472명이다. 비율은 4.2배 대
3.4배로 비슷하다. 즉 **§5.45 는 두 해상도를 똑같이 빠르게 했을 뿐 격차를 줄이진
않았다.**

그래도 올린 근거는 셋이다:

1. **`map4x` 에서는 규칙이 안 돈다.** 핵 0발은 취향이 아니라 이식 실패다.
2. **`map` 의 판당 1,072초가 오늘 아침 `map4x` 의 1,827초보다 빠르다**(§5.45 덕분).
   즉 정확도를 되찾으면서 속도는 오히려 나아졌다.
3. §4.5 가 *"전체 복제는 지도를 키우는 것을 포함한다"* 고 이미 못 박아 뒀다.

⚠ **UI 프레임률은 아직 안 쟀다.** §5.20 이 `map` 을 13fps 로 쟀지만 그건 다른
플레이어 수의 판이고 §5.45 이전이다. tick 이 73.6ms 로 예산 안에 들어가므로
시뮬레이션은 버티지만, **렌더링까지 합쳐 10Hz 를 지키는지는 확인 안 했다.**
느리면 `--size map4x` 로 내릴 수 있다.

⚠ **원본 크기에서는 아직 거의 안 일어난다 — 골드가 없어서다.** §5.31 끝 참조.

**테스트 640개**(2026-08-26). **변이 186개로 검증했다** — 2026-08-22 까지 25개,
2026-08-24 에 43개(건설 AI 15 · 정복 골드 8 · 대량 업그레이드 9 · 발사관 11),

**잡히지 않는 것이 둘 있고 둘 다 정상이다.** 관찰 가능한 차이가 없는 무동작 분기다:
`unitsOwned` 의 `1 if under_construction else u.level`(§5.30 끝) ·
`BUILD_ORDER` 에 `DEFENSE_POST` 를 넣는 것(§5.31 — 진짜 관문은 순서 목록이 아니라

적 하나가 10을 넘어야 표적이라 이미 함의된다) · 선제 대응의 "내 배" 검사
(§5.43 — `is_friendly(pid, pid)` 가 항상 참이라 이미 함의된다).
다섯 다 해당 파일에 그렇게 적어 뒀으니 파지 말 것 — 뒤 셋은 **성능용 이른 탈출**이다.

**살아남았다가 고친 변이는 지금까지 열넷인데, 열넷 다 테스트가 아니라 재료가
문제였다** — 지도가 단순해서 · 두 후보가 애초에 사거리 밖이라 · 사일로를 전부
레벨 1로 둬서 레벨 합과 개수가 같아서 · 후보가 둘뿐이라 `chance(2)` 때문에 무엇을
해도 50:50 이라서 · (§5.35 에서 다섯 더) 후보가 보너스 정원보다 적어서 · 후보를
이미 정렬된 순서로 넘겨서 · 항구를 전부 Lv1 로 둬서(**§5.34 와 같은 실수를 반복**) ·
"늘었다"만 봐서 상한을 안 재서 · 순수 함수만 재고 배선을 안 재서 ·
(§5.36 에서 다섯 더) 부작용을 안 봐서 "안 했다"와 "했다가 실패했다"가 같아서 ·
엔진 경로로는 그 분기에 도달조차 못 해서 · 상태를 테스트가 직접 세팅해 그 상태를
만드는 코드가 검사에서 빠져서 · 추격 tick 을 넉넉히 줘서 속도가 안 재져서 ·
탐욕 이동이 결국 같은 칸까지 가서 사거리가 안 재져서.
**변이가 안 잡히면 코드와 재료를 먼저 의심한다.**

### 이식 누락이 어떻게 드러났나

**새 세션은 이 표를 먼저 보여준다**(사용자 요청, 2026-08-21). 규칙을 코드로만
대조해서는 하나도 못 찾았다 — 전부 *화면에 뭔가 만들다가* 또는 *이상한 것을
확인하다가* 나왔다. 다음 누락도 같은 방식으로 나올 것이다.

| 누락 | 어떻게 드러났나 |
|---|---|
| MIRV 비용 | 건설 메뉴를 만들다 `KeyError` 로 터졌다 |
| 스폰 면역 | 사람을 방치했더니 155초에 탈락하는 걸 보고 |
| 관계도 전체 | AI 가 동맹 요청을 `rng.random() < 0.5` 로 받고 있었다 |
| 이모지 | HUD 대조 — 장식인 줄 알았는데 🖕 하나가 관계 −100 |
| 배신자 90% 거절 | 이모지를 배선하다 함께 나왔다 |
| 스폰 페이즈 | 시작 위치를 고르는 시간이 통째로 없었다 |
| **지도 규모** | 원본은 72나라 + 봇 400인데 우리는 4~6명이었다 |
| 사람 봐주기 | "왜 이렇게 빨리 죽나"를 계측하다 |
| 표적 지정 | 상수만 있고 기능이 없어 동맹으로 할 일이 없었다 |
| 퇴각 | 잘못 찍은 공격을 되돌릴 방법이 없었다 |
| 공격 비율 조작 | 슬라이더가 마우스 전용이었다(T/Y 키 누락) |
| **철거 쿨다운 30배** | 이 문서에 "10 tick" 이라 적어 두고 값을 확인 안 했다 (실제 300) |
| **상륙 퇴각 25%** | 퇴각을 만들다 — 상수는 있는데 값이 `0.0` 이고 아무도 안 읽었다 |
| **전체 금수의 봇 필터** | "편의 기능"으로 분류해 뒀는데 필터 자체가 규칙이었다 |
| **`unitsOwned` = 레벨 합** | 업그레이드를 UI 에 붙이려다 — **원본을 실행해서** 잡았다 |
| **건설=업그레이드 통합** | 같은 작업 중 — 원본엔 업그레이드 버튼이 아예 없었다 |
| **`Attack.sourceTile`** | 원본 AI 의 초소 조건을 옮기다 — 상륙과 육상 공격을 구분할 필드가 아예 없었다 |
| **정복 골드 이전** | "AI 가 왜 가난한가"를 캐다 — 원본 수입 경로를 하나씩 따라가니 네 번째가 통째로 없었다 |
| **사일로 발사관** | 핵 대량 구매의 상한(`readyMissileCount`)이 우리에게 있는지 확인하다 |
| **SAM 발사관** | 같은 확인 중 — SAM 한 기가 판의 모든 핵을 영원히 100% 막고 있었다 |
| **항구별 무역선 스폰** | "수입 공식이 틀렸나"를 대조하러 갔다가 — 공식은 맞았고 **뜨는 횟수**가 틀렸다 |
| **무역선 나포** | 같은 대조 중 — 우리는 격침시켜 골드를 증발시키고 있었다 |
| **전함 추격 이동** | 나포를 붙이니 하나도 안 잡혔다 — **전함이 아예 안 움직이고 있었다** |
| **전함 순찰 이동** | 추격만 먼저 옮기고 "절반만 옮겼다"고 적어 둔 것을 마저 옮겼다 |
| **전함 수리 후퇴** | 같은 자리 — 문서가 "남은 것은 수리 후퇴"라고 적어 둔 것을 마저 옮겼다 |
| **자리 고르기 값 함수** | "그 밖" 표에서 가장 큰 덩어리를 꺼내 옮겼다 — 미뤄 둔 것이 곧 누락이었다 |
| **전함 건조 상한** | **골드를 어디에 쓰는지 셌다** — 지출의 85%가 전함이었다 |
| **핵 AI** | 원본 AI 파일 크기를 우리 것과 대조했다 — 1,104줄 대 **열 줄**이었다 |

교훈: **UI 를 만들면 규칙 버그가 나온다.** 아무도 안 쓰는 경로는 테스트가 있어도
안 드러난다. 계측도 마찬가지다 — 원인을 캐는 측정이 규칙 누락을 찾아 준다.

### 남은 것

#### ▶ 다음 세션은 여기서 시작한다 — **UI 를 원본 해상도에서 재라**

§5.47 에서 기본 해상도를 `map`(2000×1000, 육지 651,569)으로 올렸다. 헤드리스는
확인했지만 **UI 는 안 쟀다.** §5.20 이 `map` 을 13fps 로 쟀는데 그건 플레이어
수가 다른 판이고 §5.45 이전이다.

재는 법: `python -m domynion.ui.app` 를 그대로 띄우면 이제 `map` 이다.
tick 이 73.6ms 이고 예산이 100ms(10Hz)이므로 **렌더링에 남는 것은 26ms** 다.
§5.16 이 렌더러를 타일 해상도로 다시 짜서 4.0ms 를 만들었지만, 그건 `map4x`
기준이고 `map` 은 타일이 4배다.

| 결과 | 다음 |
|---|---|
| 10Hz 를 지킨다 | 끝. 다음 항목으로 |
| 못 지킨다 | 렌더러를 본다. **어디가 느린지 먼저 재고**(§5.20 에서 세 번 헛짚었다) 고친다 |
| 도저히 안 된다 | UI 만 `map4x` 로 되돌린다. 다만 **그 판은 규칙이 다르게 돈다**는 것을 화면에 알린다 |

#### 그다음 — 밸런스를 원본과 대조한다

이제야 잴 수 있는 것이다. §5.47 판(seed 1, `map`, 9,000 tick)이 기준선이다:

| | 값 |
|---|---|
| 핵 발사 | 10발 |
| 생존 | 39명 |
| 사일로 | 31기 |
| 골드 최고 / 중앙 | 11,663,856 / 2,053,888 |
| 벽시계 | 1,072초 |

⚠ **이 숫자가 원본과 비슷한지는 모른다.** 원본을 그 규모로 돌려 본 적이 없다.
§5.30 의 방법(원본을 실행해서 값을 받아 오기)을 **판 단위로** 확장할 수 있는지가
열린 질문이다 — 지금은 함수 단위로만 대조하고 있다.

그 전에 값싼 것부터: **seed 를 여러 개 돌려 분포를 본다.** §5.46 에서 배웠듯
한 판으로는 아무것도 판정할 수 없다. 판당 18분이므로 병렬로 4~8판이 현실적이다.

#### ⚠ 남은 성능 자리

§5.45 에서 2.6배를 얻었지만 `map` 으로 올리면서 판당 1,072초가 됐다.
프로파일에서 `water_path` 가 여전히 1등(48%)이고, 다음은 이렇게 본다 —
**전부 추측이므로 고치기 전에 `cProfile` 부터 돌린다:**

- `_path_cache` 의 적중률. 항구 쌍이 늘면 캐시가 안 맞는다.
- `_advance_attacks`(13.7초, 7%) — §5.45 에서 안 건드렸다.
- `map` 으로 커지면서 순위가 바뀌었을 수 있다. **`map4x` 프로파일을 그대로
  믿지 않는다.**

| `TeamStats` · `AllianceClusters` | 표시 | 팀 모드용 | 팀 모드가 없으니 뒤 |
| 팀 모드 자체 | 규칙 | `GameMode.Team` | 우리는 FFA 만 |

~~⚠ `NationStructureBehavior` 의 무게가 올라갔다~~ — **§5.31 에서 해결했다.**
AI 가 밀도 문턱을 넘으면 새로 짓는 대신 올린다. 사람만 업그레이드를 쓸 수 있던
비대칭이 사라졌다.

**P7(증강형 테크트리)** 이 최종 목표다. 원본에 없는 것이라 근거 문서가 없고,
형태(드래프트 / 고정 루트 / 그 밖)를 **아직 정하지 않았다** — 사용자와 상의해야
하는 유일한 항목이다.

### 이 프로젝트에서 반복된 함정 (새 세션이 먼저 읽을 것)

#### ⚠ 변이 하네스를 돌리는 동안 스위트를 따로 돌리지 말 것 (2026-08-26)

하네스는 소스를 **제자리에서** 고쳤다가 되돌린다. 그 사이에 `pytest` 를 따로
돌리면 **변이된 소스로 재게 된다.** 실제로 통과하던 테스트가 실패해서 규칙이
깨진 줄 알고 한참 뒤졌는데, 두 번 다시 돌려 보니 643개가 전부 통과했다.

같은 이유로 **하네스를 강제 종료하면 소스가 변이된 채 남을 수 있다.**
`finally` 가 되돌리지만 `kill` 은 그것도 건너뛴다. 끊었으면 반드시
`git diff` 로 소스를 확인한다.

⚠ **같은 날 세 번 당했다.** 세 번째가 가장 나빴다 — 변이가 살아 있는 동안
새 테스트를 돌렸는데, 그 변이가 하필 A* 의 방문 검사를 지운 것이라 힙이
무한히 커져 **파이썬 프로세스 하나가 19GB** 를 먹었다. 다행히 다른 작업의
메모리를 확인하다 발견했다. 규칙으로 굳힌다:

> **변이 하네스가 도는 동안에는 `pytest` 도, 실측 스크립트도 새로 띄우지 않는다.**
> 끝난 것을 로그로 확인하고 시작한다.

#### ⚠ 변이가 무한 루프를 만들 수 있다 — 하네스에 시간 제한을 둔다 (2026-08-26)

A* 의 방문 검사(`if n in g: continue`)를 지우는 변이가 힙을 무한히 키웠다.
하위 프로세스가 **3.85GB**, 손으로 재현하다 만든 것은 **22.9GB** 까지 갔다.
하네스에 `timeout=180` 을 걸고 **타임아웃도 "잡힘"으로 센다** — 무한 루프는
테스트가 못 잡은 것이 아니라 잡은 것이다.


1. **편집 스크립트는 바이너리로 읽고 쓴다.** `read_text`/`write_text` 왕복이
   CRLF 파일의 줄을 두 배로 늘린다 — `ui/actions.py` 가 288 → 576줄이 된 채
   커밋됐다(커밋 `3504ad3`). ⚠ 이 항목이 오래 `§5.29` 를 가리키고 있었는데
   **그런 절이 없었다.** 지금 §5.29 는 다른 이야기다.
2. **돌연변이가 안 잡히면 테스트가 아니라 코드를 먼저 의심한다.** 죽은 방어
   코드를 세 번 찾았다(`ATTACK_RATIO_MIN` · 순위표 빈 줄 · 그 밖).
3. **기대값을 검사 대상에서 가져오지 않는다.** 나라 좌표 테스트가 자기 자신과
   비교하고 있었다.
4. **성장·감쇠가 측정을 삼킨다.** 병력 상한을 넘긴 상태로 재면 반환·손실이
   안 보인다. 대조군을 둔다. 관계 값도 같다 — 매 tick 0 쪽으로 감쇠하므로
   절대값을 못 박으면 감쇠까지 같이 재게 된다(`test_embargo_all.py`).
5. **테스트 지도가 너무 단순하면 변이가 무동작이 된다.** 내 해안이 한 칸뿐인
   지도에서는 "목적지를 매 tick 다시 고른다"가 늘 같은 답을 낸다. 변이가 살아남으면
   **그 변이가 이 지도에서 실제로 무엇을 바꾸는지**부터 확인한다(§5.29).
6. **이 문서에 이름만 적힌 항목은 확인 안 한 항목이다.** "쿨다운 10 tick" 이 30배
   틀려 있었다. 값을 옮길 때는 원본 파일을 연다 — 클론 명령은 §5.30 에 있다.
7. **반직관적인 결과에 "원본이 그렇다"고 적기 전에 원본을 돌려 본다.** 업그레이드
   값이 평평하다는 테스트 주석이 그 문장으로 끝나 있었고, **틀렸다.** 확신 있게
   쓰인 주석이 오히려 재검토를 막는다 — 근거는 "읽었다"가 아니라 "돌려서 받았다"여야
   한다(§5.30 에 되살리는 방법).
8. **테스트 지도를 작게 만들면 규칙이 아니라 지도가 답을 낸다.** 20×12(육지 120칸)로
   만든 손지도에서 두 가지가 조용히 어긋났다 — 나라 2명/120칸이
   `HIGH_NATION_DENSITY_THRESHOLD`(1/7500)를 넘어 첫 건물이 늘 항구가 됐고, 영토가
   10×10 이라 **모든 칸이 첫 건물에서 15칸 안**이라 두 번째 건물을 지을 자리가 없었다.
   테스트가 세 개 깨졌는데 셋 다 코드는 옳았다. 손지도를 만들 때는 **문턱이 걸리는
   크기인지 먼저 계산한다**(`tests/test_nation_structures.py` 의 `make_state`).
9. **진행 로그로 진행을 판단할 때, 그 로그가 지금 것인지부터 의심한다.**
   2026-08-24 에 같은 실수를 **두 번** 했다. (a) `tail -3` 창을 `[setup]` 머리줄이
   차지해 20분 동안 "1,000 tick 미도달"로 보고했는데 실제로는 127초에 도달해
   있었다. (b) 그 뒤 40분 동안 "6,000→8,000 이 22분째"로 보고했는데, 판은 이미
   1,003초에 tick 8,000 을, 1,166초에 전체를 끝내고 있었다 — 내가 읽던 파일이
   갱신되지 않았을 뿐이다.
   **둘 다 "파일에 대한 사실"을 "작업에 대한 사실"로 말한 것이다.** 1번 규칙
   ("추측하지 않는다")은 도구를 잘못 써서도 깨진다. 진행이 멈춰 보이면
   *로그가 멈춘 것인지 작업이 멈춘 것인지*를 먼저 가른다(프로세스 CPU 시간,
   파일 mtime).
10. **성능을 재기 전에 그 기계에서 무엇이 같이 돌고 있는지 본다.** §5.32 에서
   10배 회귀로 판단했다가 정정했다 — 경쟁 프로세스가 있었다. 배경 측정 두 개를
   동시에 띄워 놓고 시간을 비교하면 **둘 다 틀린 값**이 나온다. 그리고 그 전에,
   **변경이 O(1) 인지 코드로 먼저 확인한다.** §5.20 의 세 번을 합쳐 네 번째다.
11. **변이가 안 잡히면 "이 재료에서 그 변이가 무엇을 바꾸는가"를 먼저 계산한다.**
   §5.31 에서 살아남은 둘 중 하나는 재료가 문제였고(레벨 1짜리 3기로 레벨 합과
   개수를 구분하려 했다) 하나는 **진짜 무동작**이었다(초소는 비율 표에 없어
   건설 순서에 넣어도 아무 일이 없다). 5번과 같은 함정이 세 번째다.
