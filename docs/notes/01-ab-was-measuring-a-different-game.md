# 켠 쪽이 더 나빴다 — 다른 판을 재고 있었다

> Domynion · 2026-09-04 · [`17c3303`](https://github.com/yim2412/domynion/commit/17c3303) [`3e4e033`](https://github.com/yim2412/domynion/commit/3e4e033)

Domynion 은 openfront.io 를 규칙 단위로 복제한 뒤, 그 위에 **증강 드래프트**(일정
시간마다 판이 멈추고 카드 세 장 중 하나를 고르는 계층)를 얹는 프로젝트다.
증강을 다 만들고 나서 물어야 할 것은 하나였다 — **정말 판이 달라지는가.**

## 문제

같은 seed 로 증강을 켜고/끄고 돌렸다. 결과가 상식과 반대였다.

| seed | 끄고 영토 | 켜고 영토 |
|---|---|---|
| 11 | 46,594 | **20,983** |
| 22 | 75,708 | **40,316** |

켠 쪽이 **절반**이다. 증강은 전부 유리한 계수(병력 상한 +18%, 정복 비용 −14% …)뿐인데
그럴 수가 없다.

## 여기서 한 판단

**계수를 조정하지 않았다.** 값이 세거나 약해서 나온 차이라기엔 방향이 틀렸다.
유리한 계수만 넣었는데 성적이 절반이면, 재고 있는 대상이 다른 것이다.

그래서 값이 아니라 **판이 같은 판인지**를 의심했다.

## 원인

드래프트가 카드를 뽑을 때 판의 난수를 쓰고 있었다.

```python
def offer(rng, owned, count=3):
    return rng.sample(pool, k=count)     # ← 판의 rng
```

`rng.sample` 이 난수를 한 번 더 소비한다. **그 뒤로 모든 무작위가 어긋난다** —
스폰 위치도, 전투 굴림도, AI 판단도. 같은 seed 를 넣어도 **다른 판**이 된다.

증강이 나쁜 게 아니라 **A/B 가 성립하지 않고 있었다.**

## 고친 방법에 딸린 함정

드래프트 전용 난수(`_aug_rng`)를 분리했다. 다만 **켜든 끄든 만들어야 한다.**

조건부로 만들면 판 생성 시점에 `rng.getrandbits` 가 한 번 더 불려서 **고치려던
버그를 같은 자리에 다시 만든다.** 그 실수를 막는 변이 테스트를 따로 뒀다.

## 검증 — 테스트가 아니라 판으로

첫 드래프트는 750 tick 에 열린다. 그러니 **그 이전 구간은 양쪽이 같은 판이어야 한다.**

```
[7 off] 400/900 tick  영토 4769
[7 on ] 400/900 tick  영토 4769      ← 정확히 같다
```

버그가 남아 있었다면 여기서 이미 갈렸다. 진행 로그가 **자기 전제를 스스로 검증**한다.

## 고치고 다시 잰 결과

같은 seed 12개를 양쪽으로 24판(394초):

| | 끄고 | 켜고 |
|---|---|---|
| 생존 | 6/12 | 7/12 |
| **생존판 영토 중앙** | 36,732 | **108,162** |
| 조기 승리 | 1판 | **3판** |

첫 요약은 켜고·끄고 영토 중앙값이 **나란히 0** 이 나왔다. 12판 중 4판에서 죽는데
죽은 판의 0 을 섞었기 때문이다. **지표가 재료를 못 견딘 것**이라, 크기는 살아남은
판끼리만 재고 짝 판정을 넣도록 도구를 고쳤다.

## 이 건에서 남긴 규칙

> **A/B 결과가 상식과 반대면 계수보다 난수 소비를 먼저 의심한다.**
> 테스트 29개도, 전체 스위트도 전부 초록이었다. 드래프트 자체는 완벽하게 돌고
> 있었다. **이 종류는 결과를 봐야만 나온다.**
